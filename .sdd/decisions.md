## ADR-001 · Стек и ограничения платформы

**Дата:** 2026-09-26  
**Статус:** ACCEPTED  
**Автор решения:** Пользователь (GATE 0)

### Контекст
Проект создаётся с нуля, Android-приложение для личного использования.

### Решение

| Параметр | Решение |
|---|---|
| minSdk | 26 |
| targetSdk / compileSdk | 35 (последний стабильный) |
| Язык | Kotlin, Java не используется |
| UI | Jetpack Compose |
| Async | Coroutines + Flow |
| Gradle | Kotlin DSL + version catalog (libs.versions.toml) + build-logic/ |

### Последствия
- :core:model, :core:storage, :core:expr — JVM-модули, без Android-зависимостей.
- Все Android-зависимые части в :ingest:*, :app.

## ADR-002 · DoD Фазы 0

**Дата:** 2026-09-26  
**Статус:** ACCEPTED  
**Автор решения:** Пользователь (GATE 0)

### Решение
Фаза 0 закрыта только при выполнении всех 7 критериев:

1. **Живучесть**: 7 дней без переустановки и ручных перезапусков (HyperOS).
2. **Банки**: 0 пропусков операций vs история банк. приложения и SMS за неделю.
3. **Уведомления**: выборочная проверка 20 случайных → 0 пропусков.
4. **Музыка**: сессии ≥ 95% совпадения с историей Spotify/YT Music.
5. **Watchdog**: пережиты перезагрузка, обновление APK, Doze, очистка из «недавних» — source_health фиксирует восстановление без ручного вмешательства.
6. **Нет мусора**: обновления склеены, дубли и group-summary исключены.
7. **Батарея**: ≤ 2% в сутки по системной статистике.
8. **Данные**: БД зашифрована, экспорт JSON работает, «удалить всё» работает.
9. **Алерт**: уведомление при отсутствии событий N часов — проверено искусственно.

ML, категории, пайплайны — **не начинаются** пока DoD не закрыт.

## ADR-003 · Живучесть на HyperOS / Android 15 (FGS и Watchdog)

**Дата:** 2026-09-26  
**Статус:** ACCEPTED  
**Автор решения:** Пользователь (GATE 1)

### Решение
1. `dataSync` FGS запрещён (в Android 15 ограничен 6 часами/сутки).
2. По умолчанию FGS выключен: система сама биндит `NotificationListenerService`.
3. Опциональный тумблер в настройках «Режим повышенной живучести» поднимает FGS типа `specialUse` (с `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`).
4. `WorkManager` каждые 15 минут проверяет доступ и heartbeat. Если listener отключён:
   - Шаг 1: `requestRebind(ComponentName)`.
   - Шаг 2 (запасной): toggle компонента сервиса через `setComponentEnabledSetting(disable -> enable)`.
5. Онбординг: экран с пошаговой инструкцией под HyperOS/MIUI (автозапуск, контроль активности «Без ограничений», закрепление в недавних).

## ADR-004 · Очередь и порядок обработки уведомлений

**Дата:** 2026-09-26  
**Статус:** ACCEPTED  
**Автор решения:** Пользователь (GATE 1)

### Решение
1. `Channel<NotificationRawPayload>(Channel.UNLIMITED)` с ровно **одним фоновым консьюмером**.
2. **Первое действие консьюмера** — немедленный `insertRawEvent()` в БД, до любой нормализации и бизнес-логики (минимизация окна потери данных при убийстве процесса).
3. Порядок событий строго задаётся монотонным `seq` (AtomicLong), присваиваемым при помещении в очередь (`enqueue`). Системный `postTime` для сортировки не используется (немонотонен при обновлениях).
4. В `source_health` добавлена метрика текущей длины очереди канала (`queue_depth`).

## ADR-005 · Модульность нормализации (EventNormalizer)

**Дата:** 2026-09-26  
**Статус:** ACCEPTED  
**Автор решения:** Пользователь (GATE 1)

### Решение
1. `:core:storage` не зависит от нормализации.
2. Логика нормализации текста размещается в пакете `normalize` чистого JVM-модуля `:core:model` (либо `:core:normalize`).
3. `raw_event` хранится неизменяемым (as-is). Нормализованный текст — производные данные, пересчитываемые при изменении правил.

## ADR-006 · Схема хранения эмбеддингов и миграции

**Дата:** 2026-09-26  
**Статус:** ACCEPTED  
**Автор решения:** Пользователь (GATE 1)

### Решение
1. Колонка `embedding_ref` в таблицу `event` в v1 НЕ добавляется. Эмбеддинги будут вынесены в отдельную таблицу `event_embedding(event_id, model_id, model_version, vector)`.
2. В Room включён `exportSchema = true`, схемы сохраняются в Git-репозитории.
3. Миграции настраиваются через `AutoMigration` со строгими тестами миграций в CI.

## ADR-007 · Версия и конфигурация SQLCipher

**Дата:** 2026-09-26  
**Статус:** ACCEPTED  
**Автор решения:** Пользователь (GATE 1)

### Решение
1. Использовать современную библиотеку `net.zetetic:sqlcipher-android` версии 4.6.x+ (с поддержкой 16 KB page size для Android 15+).
2. Вызывать `System.loadLibrary("sqlcipher")` при старте.
3. Использовать `SupportOpenHelperFactory` для связки с Room.
4. Запрещён слепой `pickFirst "lib/*/libcrypto.so"` во избежание подхвата несовместимого OpenSSL.

## ADR-008 · Целевое тестовое физическое устройство (Poco M7)

**Дата:** 2026-09-26  
**Статус:** ACCEPTED  
**Автор решения:** Пользователь

### Контекст
Для закрытия DoD Фазы 0 требуется реальный 7-дневный прогон на HyperOS. Подключено физическое устройство Poco M7 в режиме отладки.

### Решение
1. Идентификатор устройства: `2440cbe2` (подтверждено через `adb devices`).
2. Окружение: Xiaomi HyperOS (Android 14/15).
3. Все soak-тесты, проверки живучести `NotificationListenerService`, замеры батареи (≤2% в сутки) и валидация отсутствия пропусков банковских операций проводятся непосредственно на этом устройстве.

## ADR-009 / CR-001 · Безопасная миграция Room v2 и регистрация MIGRATION_1_2 в AppModule

**Дата:** 2026-09-28  
**Статус:** ACCEPTED  
**Автор решения:** Координатор по отчёту DevOps (GATE 8)

### Контекст
При проверке развертывания на Poco M7 выявлено, что в `AppModule.kt` был оставлен `.fallbackToDestructiveMigration()`, а `MIGRATION_1_2` не зарегистрирован в `Room.databaseBuilder()`. Это создает риск потери базы догфудинга при инкременте версии.

### Решение
1. В `AppModule.kt` заменить `.fallbackToDestructiveMigration()` на явную регистрацию `.addMigrations(MIGRATION_1_2)`.
2. Интегрировать `PreMigrationBackup` перед инициализацией базы с предварительным WAL checkpoint и копированием файла в `noBackupFilesDir`.
3. Запретить деструктивную миграцию в продакшене/догфудинге.

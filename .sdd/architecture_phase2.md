# План Фазы 2 — Notification Pipeline Constructor

> **Допущения.** У меня нет доступа к репозиторию, поэтому план опирается на типичный стек: Kotlin, `NotificationListenerService`, Room, Compose, DI и `EventProcessingOrchestrator` с захардкоженной цепочкой шагов из Фазы 1.1. Имена модулей и числовые бюджеты — это предложения. Их нужно сверить с фактической структурой (см. «Открытые вопросы» в конце).

---

## 0. Главная идея Фазы 2

Фаза 1.x доказала, что **конвейер работает**. Фаза 2 должна доказать, что **конвейер конструируется**: захардкоженная цепочка превращается в декларативное, версионируемое и валидируемое описание, которое пользователь собирает сам.

Центральный архитектурный принцип — **«компилируй один раз, исполняй многократно»**:

```
PipelineDefinition  ──validate/compile──▶  CompiledPipeline  ──execute──▶  Orchestrator
(данные, JSON/Room,                       (иммутабельный, регэкспы
 версия схемы)                             скомпилированы, ссылки разрешены)
```

Горячий путь (`onNotificationPosted` → оркестратор) **никогда** не парсит, не валидирует и не использует рефлексию. Он работает только с готовым `CompiledPipeline`, который подменяется атомарно.

**Инвариант паритета.** Хардкод-конвейер Фазы 1.1 должен выражаться в новом DSL как системный пресет и давать **побитово идентичный результат** на базе догфудинга. Это главный страховочный трос всей фазы.

## 1. Цели и границы

### 1.1 Цели (In Scope)

| # | Цель | Результат |
|---|------|-----------|
| G1 | Декларативная модель конвейера | Схема DSL (Trigger → Conditions → Transforms → Actions), версия схемы, сериализация |
| G2 | Компилятор и валидатор | `PipelineDefinition → Result<CompiledPipeline, List<Diagnostic>>` с понятными ошибками |
| G3 | Каталог узлов через SPI | Контракт `NodeSpec`/`NodeExecutor`, встроенный набор узлов из логики Фазы 1.1 |
| G4 | Рантайм с горячей подменой | Атомарная замена версии без перезапуска NLS, штамп версии на каждом событии |
| G5 | Хранение и версионирование | Таблицы определений и ревизий, миграция БД 1.1 → 2 без потери догфуд-данных, откат на прошлую ревизию |
| G6 | Редактор (MVP) | **Линейный** редактор шагов с ветвлением только через условия. Без свободного графа. |
| G7 | Симуляция и Replay | Прогон черновика по историческим событиям из БД догфудинга, diff с активной версией |
| G8 | Наблюдаемость | Трассы по узлам (сэмплированные), счётчики, экран диагностики «почему сработало / не сработало» |

### 1.2 Вне рамок (явные Non-Goals)

- Свободный DAG-редактор с drag-and-drop (Фаза 3+). DSL проектируем так, чтобы его можно было расширить, но UI его не показывает.
- Пользовательские скрипты (JS, Lua, выражения с произвольным кодом). Только декларативные предикаты из каталога.
- Облачная синхронизация, аккаунты, маркетплейс пресетов. Допустим только **локальный** экспорт/импорт JSON как побочный эффект сериализации.
- ML-классификация уведомлений.
- Сетевые действия (webhooks) — отдельное решение по безопасности, выносим в Фазу 3.
- Поддержка других OEM как цель. Целевое устройство — Poco M7 / HyperOS. Остальные — best effort.

## 2. Зоны ответственности для спецификаторов

Каждая зона сдаёт спецификацию в формате: **контракт (интерфейсы/типы) → инварианты → ошибки → тест-план → бюджеты**. Межзонные интерфейсы фиксируются в 2.0. Изменения после фиксации проходят только через ADR.

| Зона | Ответственность | Отдаёт наружу | Зависит от | Ключевые вопросы спецификации |
|------|----------------|---------------|-----------|------------------------------|
| **Z1. Доменная модель и DSL** | Схема `PipelineDefinition`, типы узлов, версионирование схемы | `:pipeline:dsl` (чистый Kotlin) | — | Эволюция схемы (v1 → v2), неизвестные поля, стабильные ID узлов, канонизация JSON |
| **Z2. Компилятор и валидация** | Проверка типов, разрешение ссылок, прекомпиляция регэкспов, лимиты сложности | `Compiler`, `Diagnostic` | Z1, Z4 (API) | Детерминизм, локализуемые ошибки с путём до узла, лимиты (число узлов, длина паттерна) |
| **Z3. Рантайм исполнения** | Интеграция с `EventProcessingOrchestrator`, горячая подмена, изоляция сбоев узлов, бюджеты времени | `PipelineRuntime`, `ActivePipelineProvider` | Z2, Z4 | Семантика in-flight событий при подмене, поведение при исключении в узле, backpressure |
| **Z4. Каталог узлов (SPI)** | Контракт узла, встроенные условия/трансформации/действия | `:pipeline:nodes-api`, `:pipeline:nodes-builtin` | Z1 | Чистота узлов (побочные эффекты только в Actions), идемпотентность, защита от петель |
| **Z5. Хранение и миграции** | Таблицы определений и ревизий, миграция Room, откат | `PipelineRepository` | Z1 | Миграция без потери догфуд-данных, атомарность «сохранить и активировать», GC старых ревизий |
| **Z6. Редактор UI** | Линейный редактор, inline-диагностика, пресеты | `:feature:editor` | Z1, Z2, Z5 | Модель состояния черновика, undo, производительность на слабом GPU |
| **Z7. Симуляция и Replay** | Прогон черновика по истории, diff результатов | `ReplayEngine` | Z2, Z3 (режим без side effects), Z5 | Sandbox-режим Actions, чанкование, отмена, прогресс |
| **Z8. Наблюдаемость** | Трассы узлов, метрики, экран диагностики | `:core:diagnostics` | Z3 | Политика сэмплирования, ring buffer, срок хранения, стоимость записи |
| **Z9. Платформа / HyperOS** | Выживание NLS, rebind, онбординг разрешений, тестовый стенд | Чек-лист и `DeviceHealthMonitor` | — | Autostart, battery saver, `requestRebind`, детект отключения |

**Сквозная роль — владелец паритета.** Один человек отвечает за дифференциальный тест «Legacy 1.1 vs DSL-пресет». Он имеет право вето на мерж любой зоны, если тест краснеет.

### 3.2 Правила графа (проверяются в CI)

1. **`:pipeline:dsl`, `:pipeline:nodes-api`, `:pipeline:compiler` — без Android-зависимостей.** Их тесты идут на JVM за секунды. Там живёт основная масса новых тестов.
2. `:feature:*` не зависят друг от друга.
3. `:service:listener` меняется минимально: только перенаправление в `PipelineRuntime`. Этот модуль — самый хрупкий из-за HyperOS, трогать его без нужды не стоит.
4. Legacy-хардкод из 1.1 **не удаляется** до конца 2.2. Он живёт за флагом как эталон для теста паритета и как аварийный fallback.
5. Проверка — Gradle-плагин (например, `dependency-analysis` или собственное правило) падает на нарушениях направлений.

### 3.3 Модифицируемые модули

| Модуль | Изменение | Риск |
|--------|-----------|------|
| `EventProcessingOrchestrator` | Цепочка шагов заменяется исполнением `CompiledPipeline`; legacy-путь за флагом | Высокий → закрывается тестом паритета |
| `:core:database` | Новые таблицы `pipeline_definition`, `pipeline_revision`, `node_trace`; колонка `pipeline_revision_id` в событиях | Высокий → миграционный тест на реальной копии догфуд-БД |
| `:core:model` | Нормализованный `NotificationEvent` как вход DSL (только текстовые поля, без Bitmap) | Средний |
| `:service:listener` | Вызов нового рантайма, обработка `onListenerDisconnected` | Средний |
| `:app` | DI, навигация, флаги | Низкий |

## 4. Definition of Done Фазы 2

### 4.1 Функциональность

- [ ] Пользователь создаёт, редактирует, активирует и откатывает конвейер без перезапуска приложения.
- [ ] Пресет «Legacy 1.1» поставляется как системный и активен по умолчанию после миграции.
- [ ] Невалидный конвейер **невозможно активировать**. Диагностика указывает конкретный узел и поле.
- [ ] Replay черновика по истории показывает diff с активной версией.
- [ ] Экран диагностики отвечает на вопрос «почему это уведомление обработано так».
- [ ] Экспорт/импорт JSON с проверкой версии схемы.

### 4.2 Качество и тесты

- [ ] Все 322 существующих теста GREEN, **ни один не удалён и не ослаблен** без ADR.
- [ ] **Дифференциальный тест паритета**: 100% совпадений Legacy 1.1 и DSL-пресета на полном корпусе догфуд-БД.
- [ ] Property-based тесты: `serialize(deserialize(x)) == x`; компилятор детерминирован; валидный вход не бросает исключений.
- [ ] Покрытие строк ≥ 90% для `:pipeline:dsl` и `:pipeline:compiler`, ≥ 80% для `:pipeline:runtime`.
- [ ] Тест конкурентности горячей подмены: N событий в полёте при M подменах. Каждое событие обработано ровно одной версией, штамп версии корректен.
- [ ] Миграционный тест Room по всем путям, плюс ручная миграция **копии** реальной догфуд-БД на Poco M7 со сверкой числа записей и контрольных сумм.
- [ ] Fuzz-тест компилятора на мусорный и враждебный JSON.

### 4.3 Производительность (замер на Poco M7, serial `2440cbe2`)

Бюджеты задаются **относительно baseline 1.1**, который замеряется в подфазе 2.0. Абсолютные числа ниже — стартовые предложения.

| Метрика | Бюджет |
|---------|--------|
| p50 / p95 обработки одного уведомления (конвейер ≤ 10 узлов) | ≤ baseline + 20% и p95 ≤ 15 мс |
| Компиляция конвейера из 50 узлов | ≤ 50 мс |
| Горячая подмена (от «Активировать» до применения) | ≤ 100 мс, ноль потерянных событий |
| Прирост Java heap в фоне | ≤ 15 МБ к baseline |
| Replay 10 000 событий | ≤ 30 с, без thermal throttling, отменяем |
| Редактор: janky frames (JankStats / Macrobenchmark) | ≤ 5% |
| Cold start | ≤ baseline + 10% (с baseline profile) |
| Wakelocks, инициированные приложением в простое | 0 |

### 4.4 Надёжность на устройстве

- [ ] **72-часовой soak-догфудинг** на новой версии: ноль крэшей и ANR, ни одного необработанного отключения NLS (либо автоматический rebind ≤ 60 с).
- [ ] Выживание после перезагрузки, включения Battery Saver и очистки из «Недавних» — проверено по чек-листу.
- [ ] Защита от петель: действие, которое постит уведомление, не запускает само себя. Есть тест.
- [ ] Исключение в любом узле не роняет конвейер и не блокирует следующие события.

### 4.5 Документация

- [ ] ADR по ключевым решениям: формат DSL, компиляция против интерпретации, семантика подмены, политика трасс, отказ от свободного DAG в Фазе 2.
- [ ] Спецификация схемы DSL v1 с примерами.
- [ ] Runbook: деплой, откат, снятие Perfetto-трассы, извлечение БД с устройства.

## 5. Риски производительности на Poco M7 и митигации

Poco M7 — бюджетное устройство: SoC начального уровня, мало больших ядер, eMMC/UFS начального класса, агрессивный HyperOS. Главная угроза не в «медленном коде», а в **ОС, которая убивает то, что ей кажется лишним**, и во **внезапных всплесках нагрузки**.

| # | Риск | Причина | Митигация | Как проверяем |
|---|------|---------|-----------|---------------|
| R1 | **HyperOS отключает или убивает NLS** | Battery saver, отсутствие autostart, очистка из недавних | Онбординг-чек-лист (Autostart, «Без ограничений», закрепление в недавних); обработка `onListenerDisconnected` → `requestRebind`; `DeviceHealthMonitor` с алертом в UI; heartbeat-метрика «время с последнего события» | Soak 72 ч, сценарии из 4.4 |
| R2 | **Блокировка потока колбэка NLS** | Тяжёлая работа в `onNotificationPosted` | Колбэк только извлекает нормализованный `NotificationEvent` (без Bitmap) и кладёт его в ограниченный `Channel`. Обработка идёт на отдельном однопоточном диспетчере. Политика переполнения — коалесцирование по ключу уведомления. | Perfetto: длительность колбэка < 2 мс |
| R3 | **Катастрофический backtracking регэкспов (ReDoS)** | Пользовательские паттерны | Компиляция паттернов в компиляторе, а не на горячем пути; лимит длины паттерна и входного текста; рассмотреть **RE2J** (линейное время) для пользовательских паттернов; тайм-бюджет узла с логированием нарушений | Fuzz враждебными паттернами, бенчмарк |
| R4 | **Оверхед интерпретации и аллокаций → GC-паузы** | Рефлексия, парсинг, боксинг, копирование `extras` | `CompiledPipeline` — массив прямых вызовов без рефлексии и `Map`-lookup; не держать ссылки на `Notification`/`Bitmap`; строки извлекаются один раз; Allocation tracker в CI-бенчмарке | Macrobenchmark + heap dump |
| R5 | **Write amplification SQLite** | Запись трассы каждого узла для каждого события | Трассы пишутся в in-memory ring buffer. На диск — только при ошибке, при сэмплировании (например, 1%) или при включённом режиме отладки. Batch-запись в одной транзакции, WAL, единственный writer. TTL-очистка через WorkManager. | Счётчик записей/мин, размер БД за 72 ч |
| R6 | **Гонки при горячей подмене** | Событие в полёте, пока меняется версия | `AtomicReference<CompiledPipeline>`: событие захватывает ссылку один раз при входе и исполняется целиком на этой версии; ID ревизии пишется в запись события; старая версия собирается GC | Тест конкурентности из 4.2 |
| R7 | **Всплески уведомлений** (чаты, групповые сообщения, прогресс загрузки) | Десятки событий в секунду | Ограниченная очередь, коалесцирование обновлений одного ключа, отдельный rate limiter на Actions | Стенд: `adb -s 2440cbe2 shell cmd notification post ...` в цикле, 50 событий/с |
| R8 | **Петли действий** | Action постит уведомление, которое снова триггерит конвейер | Игнор собственного пакета по умолчанию; hop-counter в extras своих уведомлений; rate limit на правило | Юнит- и интеграционный тест |
| R9 | **Троттлинг при Replay** | Длинный CPU-bound прогон | WorkManager, чанки по ~500 событий с `yield()`, приоритет фона, отмена, пауза при высокой температуре (`PowerManager.getThermalHeadroom` где доступно); Actions в sandbox — no-op | Replay 10k событий с мониторингом температуры |
| R10 | **Jank редактора на слабом GPU** | Recomposition, нестабильные типы | `LazyColumn` с ключами, `@Immutable`/`@Stable` модели, derived state; **baseline profile**, R8 full mode; без тяжёлых анимаций | JankStats, Macrobenchmark `FrameTimingMetric` |
| R11 | **Длинная миграция БД при старте** | Большая догфуд-БД, добавление колонок и индексов | Миграция только добавляет структуру, без переписывания истории; тяжёлые бэкфиллы выносятся в фоновый воркер; замер времени миграции на копии реальной БД | Миграционный тест на устройстве |

### Измерительный стенд (готовится в 2.0)

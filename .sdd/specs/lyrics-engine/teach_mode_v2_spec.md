# Спецификация SPEC-TEACH-06: TeachMode 2.0 (Two-Tier Ingestion & Jsoup DOM Engine)

**Статус:** APPROVED  
**Архитектурная зона:** `lyrics-engine` & `media-ui`  
**Дата:** 2026-10-28  

---

## 1. Контекст и Проблема
Предыдущая реализация TeachMode страдала от критических архитектурных изъянов:
1. **Смешение ручной привязки и создания правил:** Пользователь не мог просто сохранить найденный текст для текущей песни без принудительного создания правила с фейковым шаблоном `/search?q={query}`.
2. **Ломкий парсинг HTML на регулярных выражениях:** Метод `extractBalancedTags` ломался на вложенных тегах, современных атрибутах и динамических страницах.
3. **Отсутствие двухшагового поиска:** Поиск по сайту не поддерживал селектор ссылок поисковой выдачи (`searchResultSelector`) и ранжирование кандидатов по схожести.
4. **Отсутствие адресной строки:** Пользователь не мог вставить прямую ссылку на песню, застревая в редиректах Google и AMP-страницах.

---

## 2. Архитектурный инвариант (Tier A vs Tier B)
- **Tier A (Manual Track Binding):** Прямая привязка выделенного текста к `targetTrack` в Room (`updateLyrics` + `saveLyrics`) в 1 тап. Не зависит от правил, валидации поиска или парсера. Ошибки Tier B не блокируют Tier A.
- **Tier B (Autonomous Site Rules):** Декларативные правила поиска и парсинга сайта с двухшаговым поиском, селектором выдачи, Jsoup-экстрактором, поддержкой статусов (`ACTIVE`, `DRAFT`) и режимов (`LYRICS`, `CHORDS`, `MIXED`).

## 4. Контракты компонентов

### 4.1. Jsoup DOM Extractor (`CustomRuleLyricsProvider.kt`)
- `extractContentJsoup(html: String, contentSelector: String, stripSelectors: List<String>, mode: String)`:
  - Парсинг через `org.jsoup.Jsoup`.
  - Удаление `stripSelectors`.
  - Преобразование `<br>` в `\n`, блочных элементов в переносы строк.
  - Сохранение пробелов и выравнивания аккордов при режиме `CHORDS`/`MIXED`.
- `resolveSongUrl(searchHtml: String, selector: String?, title: String, artist: String, domain: String)`:
  - Извлечение всех ссылок по `searchResultSelector` (или `<a href>`).
  - Ранжирование кандидатов по заголовку и артисту (Levenshtein / Token similarity).
  - Отсечение кандидатов с уверенностью ниже порога (0.4f).

### 4.2. UI Inspector & Address Bar (`TeachModeScreen.kt`)
- Коллапсируемая адресная строка: ввод URL, кнопка «Перейти», детекция редиректов Google (`/url?q=...`) и AMP (`/amp/...`).
- Блокировка опасных схем (`javascript:`, `file:`).
- Раздельные кнопки действий:
  - **Primary:** `«Привязать к треку»` (Tier A).
  - **Secondary:** `«Сохранить как правило сайта»` (Tier B).

### 5.2. Решения
1. **Выделение по умолчанию = блок.** Тап поднимает выделение от элемента до ближайшего «текстового контейнера» (элемент с ≥2 строками: `<pre>`, несколько `<br>`, несколько блочных детей с текстом), не выше `article/main/body`. Кнопка «Расширить» остаётся; добавляется «Сузить» (вернуть предыдущий уровень).
2. **Защита замены (Tier A).** Если у трека уже есть текст выбранного типа и новый заметно короче (< 60 % непустых строк старого или < 60 % символов), перед записью показывается диалог «Заменить текст из N строк на M строк?» с «Заменить»/«Отмена». Без существующего текста — 1 тап, как в R1.
3. **Одна функция привязки** `TeachModeBindingHelper.bindManualContentToTrack` в `libraryTransaction`; в режиме «Текст» существующие аккорды сохраняются как есть (выделение не парсится как аккорды); атрибуция источника пишется всегда. Трек фиксируется при открытии экрана (`remember`), смена трека в плеере не перенаправляет запись.
4. **Шаблон поиска из навигации (R2).** Пока TeachMode открыт, экран запоминает загруженные URL того же домена; если в пути или параметре URL встречается закодированный запрос (название/исполнитель трека или текст, введённый на сайте), он заменяется на `{query}`. Найденный шаблон подставляется в диалог; при отсутствии поле пустое — правило можно сохранить только черновиком. Селектор ссылок выдачи выводится из ссылки, по которой пользователь перешёл со страницы поиска на страницу песни (необязателен).
5. **Активация только после проверки (R9/R10).** В диалоге правила кнопка «Проверить» выполняет полный конвейер для целевого трека (сеть → ранжирование → извлечение) и показывает запрос, URL кандидата, уверенность, режим, первые строки или типизированную ошибку. «Включить правило» доступно только после успешной проверки; иначе — «Сохранить черновик». Черновик не исполняется даже при `isEnabled = true`.
6. **Ранжирование (R7).** Детерминированная оценка 0..1 по токенам названия (вес 0.6) и исполнителя (0.4) по тексту ссылки, `title` и пути URL; штраф за конфликтующие маркеры версий (live/remix/acoustic/cover и т. п., если их нет в треке); отсев ссылок поиска/служебных страниц и чужих доменов. Порог `MIN_CONFIDENCE = 0.6`; если второй кандидат ближе чем `AMBIGUITY_MARGIN = 0.08` к лучшему и ведёт на другой URL — `AmbiguousMatch`. Фолбэков «на первую ссылку» нет.
7. **Типизированный результат (R11).** `CustomRuleLyricsProvider.resolve(track): RuleOutcome` (sealed: `Success`, `NotFound`, `LowConfidence`, `AmbiguousMatch`, `InvalidRule`, `InvalidSelector`, `Blocked`, `Timeout`, `NetworkFailure`, `UnsupportedDynamicContent`, `WebViewUnavailable`, `EmptyContent`, `Cancelled`, `Draft`). `getLyrics` сохраняет текущий контракт `LyricsResult` (каскад не меняется), превью использует `resolve`. Сеть правил: только `https`, хост = домен правила или его поддомен, запрет IP/localhost/приватных адресов (в т. ч. после DNS), ≤ 5 редиректов с проверкой каждого, ответ ≤ 2 МБ, таймауты 6/8 с, без повторов на 403/429.
8. **WebView-фолбэк (R6).** Отдельный `RuleWebViewRenderer`: только главный поток, один сеанс одновременно, таймаут 15 с, опрос селектора каждые 300 мс, без JS-моста, без файлового доступа, уничтожение в `finally`, отмена корутины прерывает загрузку. Вызывается только в интерактивном контексте (проверка правила в TeachMode). В автоматическом каскаде рендерера нет → `UnsupportedDynamicContent`, каскад идёт к другим источникам. Фолбэк пробуется только при «пустом контенте при успешном ответе», не при сетевых ошибках и не при невалидном селекторе.
9. **Режимы (R9).** Единый обход DOM: `LYRICS` — построчная обрезка, элементы `chordsSelector` вырезаются; `CHORDS` и `MIXED` — сохранение пробелов (выравнивание аккордов). Неизвестная `schemaVersion` (> 2) → `InvalidRule`. Regex-извлекатель убран из пути извлечения; устаревшая запись `itemprop=x` нормализуется в `[itemprop="x"]`.
10. **Фикстуры (R5).** Три сайта с реалистичной структурой DOM и синтетическим текстом (вместо настоящих песен); ожидаемый URL и ожидаемый текст лежат отдельными файлами (`expected_url.txt`, `expected.txt`), сравнение точное; негативные фикстуры: неоднозначная выдача, чужая песня, пустая выдача, относительные ссылки, дубликаты.

### 5.3. Вне рамок этапа
- Подключение WebView-рендерера к автоматическому каскаду в foreground (требует правок `MainActivity`/`AppScaffold`) — отдельная задача.
- Desktop (`DesktopCustomSources`) не проверяет `status` правила; правила с Android туда не синхронизируются — зафиксировать в бэклоге.

### 5.4. Критерии приёмки этапа 4
- [ ] Тап в инспекторе выделяет блок, а не строку (проверка на фикстурной странице через инструментальный/JS-тест или вручную на телефоне).
- [ ] Замена существующего текста заметно более коротким требует подтверждения; без текста — 1 тап.
- [ ] Одна функция привязки; режим «Текст» не меняет аккорды; ошибка БД оставляет экран открытым с выделением.
- [ ] Нет русских литералов в `TeachModeScreen.kt`; RU/EN строки; plurals; нет `e.message` в UI.

- [ ] Golden-тесты трёх сайтов: точный URL и точный текст из независимых файлов ожиданий.

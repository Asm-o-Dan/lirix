# SPEC-MEDIA-FAV-01: ручное избранное, сообщения мессенджеров, достоверность автопоиска

**Уровень:** 2 (схема Room 14→15, архив библиотеки, Android + Desktop)
**Источник:** `.sdd/reports/UI_UX_REVIEW_20261101.md`, раздел «Медиатека» и P2; план этапа 5.
**Статус:** APPROVED v1 — решения D1–D5 согласованы с пользователем 2026-11-01 (D2 и D4 изменены по его ответам).
**Инварианты:** AGENTS §5.5, §7.1, §7.4, §7.5.

## 1. Проблема и факты

Данные с телефона пользователя (копия `event_engine.db`, v14, 2026-11-01, только агрегаты):

| Факт | Число |
|---|---|
| Треков, которые проходят автоправило (≥5 прослушиваний или ≥15 мин), но не в избранном | 62 |
| Избранных, которые автоправило поставить не могло (ручная установка) | 8 из 199 |
| Записей с исполнителем «Голосовое сообщение» / «Видеосообщение» (Telegram, AyuGram) | 21, из них 12 в избранном |

1. **Автоправило перекрывает ручной выбор.** `MusicDao.addListeningCredit` (`CASE WHEN totalDurationMs + :deltaMs >= 900000 THEN 1`) и `MonotonicSessionRecorder.record` (`playCount >= 5`) ставят `isFavorite = 1` при каждом прослушивании. Снятое пользователем «сердце» возвращается. 62 трека из таблицы выше — это именно снятые вручную: автоправило оставило бы их в избранном.
2. **Сообщения мессенджеров считаются музыкой.** Telegram и его форки публикуют MediaSession с `artist = "Голосовое сообщение"` / `"Видеосообщение"` (в английском интерфейсе — `"Voice message"` / `"Video message"`) и `title = имя отправителя`. Чёрный список по пакету не подходит: в Telegram слушают и музыку (на телефоне — 13 музыкальных треков из AyuGram).
3. **Недостоверный автопоиск.** Трек «09 / Unknown Artist» получил текст из LRCLIB. Цифровое название без исполнителя не идентифицирует песню (AGENTS 7.4).

## 2. Решения

### D1. Хранение ручного выбора — колонка `favoriteUserSetAt`

`music_tracks.favoriteUserSetAt INTEGER DEFAULT NULL` (поле `TrackEntity.favoriteUserSetAt: Long? = null`).

- `NULL` — пользователь ничего не выбирал, автоправило работает как раньше.
- Время в мс — время последнего ручного выбора. `isFavorite` остаётся итоговым значением, так что запросы, индексы и UI не меняются.
- Время, а не флаг, нужно, чтобы при слиянии архивов с двух устройств побеждал более поздний ручной выбор.

Любое ручное действие ставит отметку: `MusicDao.setFavorite`, `MusicDao.toggleFavorite`. Их уже вызывают все экраны Android (`HistoryScreen`, `LibraryScreen`, `NowPlayingScreen`, `MusicFeatureEngine.toggleFavorite`) и Desktop (`DesktopLibraryRepository.favorite`). Поэтому UI-файлы менять не нужно.

Автоматика ставит `isFavorite = 1` только при `favoriteUserSetAt IS NULL`:
- `addListeningCredit`: `CASE WHEN favoriteUserSetAt IS NULL AND totalDurationMs + :deltaMs >= 900000 THEN 1 ELSE isFavorite END`.
- `MonotonicSessionRecorder.record`: если `oldTrack.favoriteUserSetAt != null`, то `isFavorite = oldTrack.isFavorite`. Отметка переносится через `copy`.
- `MusicFeatureEngine.recordPlayback` (чистая функция, сейчас вызывается только из тестов): то же правило, отметка сохраняется.

Сбросить ручной выбор и вернуть автоматику нельзя. Это сознательно: интерфейса для этого нет и в этом этапе не будет.

### D2. Миграция 14→15 без вывода ручного выбора

```sql
ALTER TABLE music_tracks ADD COLUMN favoriteUserSetAt INTEGER DEFAULT NULL;
```

Решение пользователя (2026-11-01): ручной выбор из существующих данных **не выводится**, у всех треков отметка `NULL`. Значит, 62 снятых трека один раз вернутся в избранное при следующем прослушивании. После повторного снятия выбор сохранится. Значение `isFavorite` миграция не меняет. Миграция не разрушает данные: если удалить колонку, вернётся прежнее поведение.

Миграции: Android `AppDatabase.MIGRATION_14_15` (путь 12→14→15 Room собирает из существующих), Desktop `MIGRATION_14_15`. SQL общий, лежит в commonMain.

### D3. Архив библиотеки (v1/v2)

- Новое поле помечено `@EncodeDefault(NEVER)`, как `listeningIntervalsJson` и `sourceAttributionJson`. Контрольная сумма старых архивов v1/v2 (без поля) пересчитывается так же, как раньше. Версия архива остаётся 2: поле необязательное, старые версии приложения его игнорируют (`ignoreUnknownKeys`).
- Правило слияния `isFavorite`:
  - у обеих сторон есть отметка — берём значение с более поздней отметкой; при равенстве — локальное;
  - отметка только у одной стороны — берём её значение и её отметку;
  - отметок нет — как раньше (`old || incoming`).

### D4. Предустановленные правила чёрного списка для сообщений

Четыре правила `ARTIST / EXACT` (без учёта регистра, как работает `BlacklistMatcher`):

| id | шаблон |
|---|---|
| `builtin:messenger-voice-ru` | `Голосовое сообщение` |
| `builtin:messenger-video-ru` | `Видеосообщение` |
| `builtin:messenger-voice-en` | `Voice message` |
| `builtin:messenger-video-en` | `Video message` |

- Правила добавляются включёнными (`INSERT OR IGNORE`) в миграции 14→15 и при создании новой базы (`onCreate` на Android и Desktop). Пользователь видит их в обычном списке «Чёрного списка» и может выключить или удалить. Удалённое правило не возвращается: миграция выполняется один раз.
- Влияют только на новые прослушивания (существующий фильтр при записи). **История не удаляется**: миграция ничего не чистит.
- `BlacklistViewModel.toggleRule` сейчас при повторном включении правила сразу удаляет совпадающие треки без подтверждения. Для правил `builtin:*` (решение пользователя 2026-11-01): при включении правило сразу начинает фильтровать новые прослушивания. Если в медиатеке есть совпадающие записи, появляется диалог «Удалить N записей из истории?» с кнопками «Удалить» и «Оставить». «Удалить» чистит треки и сессии, в снэкбаре есть «Отменить»; отмена возвращает треки, а правило остаётся включённым. «Оставить» или закрытие диалога ничего не удаляет. Для своих правил поведение не меняется.
- Чтобы убрать уже накопленные 21 запись, достаточно выключить и снова включить готовое правило и подтвердить удаление.
- При слиянии архивов правила объединяются по id, как и сейчас.

### D5. Не искать текст автоматически при «неизвестный исполнитель + цифровое название»

Общая функция в commonMain: `AutomaticLookupEligibility.isEligible(title, artist)`. Она возвращает `false`, если одновременно:
- исполнитель неизвестен: пустой или из `WrappedStatsEngine.UNKNOWN_ARTIST_NAMES` («Unknown Artist», «Неизвестный исполнитель» и т. п.);
- название после обрезки пробелов состоит только из цифр, пробелов и знаков `. _ - # ( )` и содержит хотя бы одну цифру («09», «001», «01 -», «#3»).

Где применяется:
- Android: `AutomaticLookupCoordinator.runOperation` возвращает пустой результат до сетевого запроса. Экран показывает «не найдено», ручной поиск и привязка (AGENTS 7.3) работают как раньше.
- Desktop: `DesktopLyricsService.onTrackChanged` после проверки сохранённого текста показывает пустое состояние без поиска (AGENTS 7.5 — одинаковое поведение).
- Уже сохранённые тексты не удаляются: решение пользователя или старый результат остаются.

«69 / Anacondaz» и «01 / Филипп Волошин» проходят: исполнитель известен.

## 3. Критерии приёмки

1. Снятое вручную «сердце» не возвращается после ≥5 прослушиваний или ≥15 минут (оба пути: `addListeningCredit` и `record`). Трек без ручного выбора по-прежнему попадает в избранное автоматически.
2. Реальная миграция 14→15 (Android Robolectric и Desktop bundled SQLite) сохраняет строки и `isFavorite`, отметка у всех `NULL`, добавляет 4 правила, не трогает существующие правила; удалённое правило не возвращается при повторном открытии.
2a. Включение готового правила без подтверждения ничего не удаляет; после подтверждения удаляет совпадающие треки, отмена их возвращает и не удаляет правило.
3. Архив без поля (v1/v2) расшифровывается с проверкой суммы; слияние соблюдает D3.
4. Трек с исполнителем «Голосовое сообщение» от `org.telegram.messenger` не записывается; музыка из того же пакета записывается.
5. Для «09 / Unknown Artist» автоматический поиск не вызывается (Android и Desktop); для «69 / Anacondaz» вызывается.
6. Полный прогон `./gradlew --continue :shared:allTests :app:testDebugUnitTest :desktop:test` проходит, кроме известных `ShareCardGeneratorTest` / `ChordTransposerRepairTest`.

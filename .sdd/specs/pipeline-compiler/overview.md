# Спецификация: zone/pipeline-compiler

## Модуль: `:pipeline:compiler` · Зона: `zone/pipeline-compiler` · Фаза 2: «Конструктор конвейеров» · Статус: `PROPOSED`

---

### 1. Назначение, архитектурный контекст и границы модуля

Модуль `:pipeline:compiler` является чистым Kotlin JVM модулем (`kotlin-jvm`), свободным от любых зависимостей Android OS (`android.*`, `androidx.*`), базы данных Room, SQLite или UI-фреймворков. Модуль реализует статический валидатор, семантический анализатор и оптимизирующий компилятор декларативного AST конвейера (`PipelineDefinition`, модуль `:pipeline:dsl`) в иммутабельный, высокопроизводительный исполняемый граф (`CompiledPipeline`), готовый к горячей подмене в рантайме `:pipeline:runtime`.

#### 1.1. Роль в архитектуре Фазы 2 (принцип «Компилируй один раз, исполняй многократно»)

В архитектуре Фазы 2 конвейер разделен на три независимых представления:
1. **Декларативное AST (`PipelineDefinition`, `:pipeline:dsl`):**
   - Человекочитаемая, сериализуемая в JSON, версионируемая и редактируемая структура данных.
2. **Скомпилированный граф (`CompiledPipeline`, `:pipeline:compiler`):**
   - Иммутабельный исполняемый граф с плоским массивом прямых функциональных вызовов, разрешенными индексами слотов памяти (регистровая модель `Frame`), прекомпилированными безопасными регулярными выражениями RE2/J и битовой маской требуемых полей входа (`requiredInputMask`).
3. **Исполняющий рантайм (`PipelineRuntime`, `:pipeline:runtime`):**
   - Горячий путь исполнения событий (`onNotificationPosted` → `submit(eventId)`), захватывающий атомарную ссылку `AtomicReference<CompiledPipeline>`.

```
┌────────────────────────────────────────────────────────┐
│         Декларативный уровень (:pipeline:dsl)          │
│                  PipelineDefinition                    │
│     (JSON AST, schemaVersion=1, Stages, Conditions)    │
└───────────────────────────┬────────────────────────────┘
                            │
                  validate / compile (Background Worker)
                  [SLA: <= 50ms на Poco M7 / HyperOS]
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│         Скомпилированный уровень (:pipeline:compiler)  │
│                   CompiledPipeline                     │
│  (Иммутабельный, регистровые слоты, RE2/J, DAG-индексы)│
└───────────────────────────┬────────────────────────────┘
                            │
                   AtomicReference.set() (Hot swap < 100ms)
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│         Горячий рантайм (:pipeline:runtime)            │
│             onNotificationPosted -> execute            │
│   (Zero reflection, Zero runtime Map lookup, < 15ms)   │
└────────────────────────────────────────────────────────┘
```

#### 1.2. Фундаментальные архитектурные инварианты

1. **Чистый Kotlin JVM (Zero Android Dependencies):**  
   Никаких импортов `android.content.Context`, `android.os.Bundle` или `android.service.notification.StatusBarNotification`. Входящие данные уведомления представляются в компиляторе абстрактной схемой полей ввода. Модуль компилируется и верифицируется в JVM-тестах за считанные секунды.
2. **Исключение `java.util.regex` и `kotlin.text.Regex`:**  
   Строжайший архитектурный запрет на использование бэктрекинговых регулярных выражений стандартной библиотеки Java/Kotlin. Все регулярные выражения компилируются исключительно через `com.google.re2j.Pattern`, гарантирующий линейное время исполнения $O(n \cdot m)$ и математическую защиту от катастрофического отката (ReDoS). Запрет контролируется статическим анализом байткода и ArchUnit-тестами.
3. **Безотказность компилятора (No Unhandled Exceptions):**  
   Метод компиляции **никогда** не выбрасывает непроверяемых исключений наружу (`Throwable` не покидает границ компилятора). Любой внутренний сбой перехватывается и трансформируется в структурированную диагностику с кодом `E0000 InternalCompilerError` и указанием проблемного узла.
4. **Строгий детерминизм:**  
   Одинаковый входной объект `PipelineDefinition` всегда порождает побитово идентичный `CompiledPipeline`, идентичную раскладку регистровых слотов и идентично упорядоченный список диагностик. Это гарантирует надежность Golden-тестов и корректность кеширования скомпилированных пайплайнов по каноническому SHA-256 хешу.
5. **Zero Allocation & Zero Reflection на горячем пути:**  
   Скомпилированный пайплайн в горячем цикле не выполняет поиск по строковым ключам (`Map.get`), не использует Java Reflection или MethodHandles, не выделяет временных объектов и не осуществляет боксинга примитивных типов (`Long`, `Boolean`, `Double`). Все переменные контекста преобразуются в целочисленные индексы плоского массива `Frame`.
6. **Двухфазная изоляция эффектов (Two-Phase Effect Buffering):**  
   В процессе прогона конвейера действия (`ActionDefinition`) не производят немедленных мутаций внешнего мира. Они аккумулируются в кольцевом или предвыделенном буфере эффектов (`EffectBuffer`). Побочные эффекты коммитятся атомарно только при успешном завершении конвейера с терминальным сигналом `PASS`.

### 2. Публичный контракт компилятора (`PipelineCompiler`)

Компилятор предоставляет потокобезопасный интерфейс без сохранения состояния между вызовами.

#### 2.1. Интерфейс `PipelineCompiler` и результат компиляции

```kotlin
package com.example.npc.pipeline.compiler

import com.example.npc.pipeline.dsl.PipelineDefinition

/**
 * Главный контракт компилятора конвейера обработки событий.
 * Потокобезопасен, не имеет внутреннего мутируемого состояния.
 */
interface PipelineCompiler {
    /**
     * Выполняет многопроходную статическую валидацию и компиляцию декларативного AST.
     *
     * @param definition Декларативное описание конвейера (DSL AST).
     * @return [CompilationResult.Success] с иммутабельным графом при отсутствии ошибок (может содержать warnings),
     *         либо [CompilationResult.Failure] со списком обнаруженных ошибок и предупреждений.
     */
    fun compile(definition: PipelineDefinition): CompilationResult
}

/**
 * Результат компиляции декларативного конвейера.
 */
sealed interface CompilationResult {
    /**
     * Полный список диагностических сообщений (ошибки, предупреждения, инфо),
     * отсортированный детерминированно в порядке следования узлов в документе.
     */
    val diagnostics: List<CompilationDiagnostic>

    /**
     * Успешная компиляция. Исполняемый граф готов к горячей подмене в рантайме.
     *
     * @property pipeline Иммутабельный скомпилированный граф конвейера.
     * @property diagnostics Список нефатальных замечаний (WARNING, INFO).
     */
    data class Success(
        val pipeline: CompiledPipeline,
        override val diagnostics: List<CompilationDiagnostic> = emptyList()
    ) : CompilationResult

    /**
     * Ошибка компиляции. Конвейер не может быть исполнен.
     *
     * @property diagnostics Список диагностик, содержащий как минимум одну диагностику со статусом ERROR.
     */
    data class Failure(
        override val diagnostics: List<CompilationDiagnostic>
    ) : CompilationResult {
        init {
            require(diagnostics.any { it.severity == DiagnosticSeverity.ERROR }) {
                "CompilationResult.Failure must contain at least one ERROR diagnostic"
            }
        }
    }
}
```

#### 2.2. Модель диагностик (`CompilationDiagnostic`) и локализация в UI

Для подсветки ошибок непосредственно в визуальном редакторе UI диагностика содержит нормализованный путь RFC 9535, идентификатор этапа, целевой элемент и опциональный текстовый диапазон (`TextSpan`).

```kotlin
package com.example.npc.pipeline.compiler

/**
 * Уровень важности диагностического сообщения.
 */
enum class DiagnosticSeverity {
    /** Блокирует исполнение и генерацию CompiledPipeline. */
    ERROR,
    /** Не блокирует компиляцию, указывает на потенциальные проблемы (мертвый код, неиспользуемые переменные). */
    WARNING,
    /** Информационное сообщение (оптимизации, рекомендации по стилю). */
    INFO
}

/**
 * Объект диагностического сообщения компилятора.
 */
data class CompilationDiagnostic(
    /**
     * Стабильный уникальный код ошибки/предупреждения (например, "P1001", "P2101", "P3001").
     * Используется для локализации (i18n), программной обработки и автоматических тестов.
     */
    val code: String,

    /**
     * Уровень важности сообщения.
     */
    val severity: DiagnosticSeverity,

    /**
     * Человекочитаемое описание проблемы на английском языке (дефолтная локализация).
     */
    val message: String,

    /**
     * Ключ локализации для UI редактора (например, "diag.error.regex_syntax").
     */
    val messageKey: String,

    /**
     * Параметры подстановки в шаблон локализации.
     */
    val messageArgs: List<String> = emptyList(),

    /**
     * Точное расположение ошибки в декларативном документе.
     */
    val location: SourceLocation,

    /**
     * Смежные локации, связанные с ошибкой (например, "переменная ранее определена здесь").
     */
    val relatedLocations: List<SourceLocation> = emptyList(),

    /**
     * Дополнительная подсказка для пользователя по устранению ошибки.
     */
    val hint: String? = null,

    /**
     * Предлагаемые автоматические исправления для редактора (Quick Fixes).
     */
    val quickFixes: List<QuickFix> = emptyList()
)

/**
 * Точное указание места возникновения проблемы в структуре AST.
 */
data class SourceLocation(
    /**
     * Нормализованный путь RFC 9535 JSONPath.
     * Пример: "$['stages'][2]['condition']['conditions'][1]['pattern']"
     */
    val jsonPath: String,

    /**
     * Целевой элемент подсветки: значение (VALUE) или имя свойства (KEY).
     */
    val target: Target = Target.VALUE,

    /**
     * Идентификатор ближайшего родительского этапа (Stage ID), если применимо.
     * Обеспечивает стабильность привязки в UI при вставке/удалении других стадий.
     */
    val stageId: String? = null,

    /**
     * Диапазон символов внутри декодированной строки (UTF-16 code units) для строковых полей (regex, выражения).
     * Полуоткрытый интервал [start, end).
     */
    val span: TextSpan? = null
)

enum class Target {
    /** Подсвечивается значение поля (например, невалидный regex в строке). */
    VALUE,
    /** Подсвечивается имя ключа (например, неизвестное свойство в объекте). */
    KEY
}

/**
 * Диапазон символов в UTF-16 code units декодированной строки (соответствует Kotlin String и Compose TextRange).
 */
data class TextSpan(
    val start: Int,
    val end: Int
) {
    init {
        require(start >= 0) { "Start must be non-negative: $start" }
        require(end >= start) { "End ($end) must be >= start ($start)" }
    }
}

/**
 * Предложение автоисправления для UI редактора.
 */
data class QuickFix(
    val id: String,
    val title: String,
    val targetPath: String,
    val replacementJson: String
)
```

### 3. Реестр диагностических кодов (Diagnostic Code Registry)

Коды разбиты на диапазоны по пассам валидации:
- `P1xxx`: Структурная валидация и схема DSL.
- `P2xxx`: Валидация регулярных выражений, RE2/J и ReDoS Guard.
- `P3xxx`: Проверка типов, таблица символов и контракты данных.
- `P4xxx`: Поток управления (CFG), достижимость и лимиты сложности.
- `E0xxx`: Внутренние ошибки компилятора.

| Код | Уровень | Описание | Подсказка / Действие в UI |
|---|---|---|---|
| **P1001** | ERROR | Неподдерживаемая версия схемы `schemaVersion` | Укажите поддерживаемую версию схемы (`1`) |
| **P1002** | ERROR | Недопустимый формат идентификатора (`id`) | ID должен соответствовать маске `^[a-z0-9_-]{3,64}$` |
| **P1003** | ERROR | Дубликат идентификатора этапа (`stage.id`) | Назначьте этапу уникальный идентификатор |
| **P1004** | ERROR | Конвейер не содержит ни одного триггера | Добавьте хотя бы один триггер источника (`NOTIFICATION`, `SMS` или `MEDIA`) |
| **P1005** | ERROR | Конвейер не содержит ни одного этапа | Добавьте хотя бы один этап обработки |
| **P1006** | ERROR | Превышено максимальное число этапов ($> 50$) | Разделите логику на несколько независимых конвейеров |
| **P1007** | ERROR | Этап не содержит ни трансформаций, ни действий | Добавьте хотя бы одну трансформацию или действие, либо удалите этап |
| **P1008** | ERROR | Пустое или пробельное имя (`name`) | Укажите осмысленное имя этапа или конвейера |
| **P1009** | ERROR | Неизвестное поле в объекте схемы DSL | Удалите неподдерживаемое свойство из спецификации |
| **P2001** | ERROR | Превышена допустимая длина регулярного выражения ($> 256$) | Сократите паттерн или разбейте его на несколько условий |
| **P2002** | ERROR | Синтаксическая ошибка RE2/J в регулярном выражении | Исправьте синтаксис регулярного выражения по спецификации RE2 |
| **P2003** | ERROR | Обнаружен неподдерживаемый бэктрекинг-синтаксис (Lookahead / Lookbehind) | RE2/J не поддерживает `(?=...)`, `(?!...)`, `(?<=...)`, `(?<!...)`. Используйте линейный матчинг |
| **P2004** | ERROR | Обнаружены обратные ссылки (Backreferences `\1`–`\9`) | Обратные ссылки требуют бэктрекинга и запрещены из соображений защиты от ReDoS |
| **P2005** | ERROR | Обнаружены сверхтяжелые вложенные повторения (ReDoS Risk) | Произведение вложенных квантификаторов превышает 1000 |
| **P2101** | INFO | Регулярное выражение является литералом без метасимволов | Паттерн оптимизирован в точный строковый поиск `contains` / `startsWith` |
| **P3001** | ERROR | Чтение неопределенной переменной (Use Before Definition) | Переменная не была инициализирована ни на одном из предшествующих путей |
| **P3002** | ERROR | Переменная определена не на всех путях выполнения | Инициализируйте переменную во всех предшествующих ветках до точки слияния |
| **P3003** | ERROR | Попытка записи в защищенное поле ввода `input.*` | Поля `input.*` доступны только для чтения |
| **P3004** | ERROR | Несоответствие типов данных (Type Mismatch) | Ожидался тип $T_1$, но предоставлен тип $T_2$ |
| **P3005** | ERROR | Нарушен контракт входных данных узла | Узел требует наличия валидированного источника или контекстной переменной |
| **P3101** | WARNING| Мертвая запись в переменную (Dead Store) | Значение записано в переменную, но больше никогда не читается |
| **P3102** | WARNING| Неиспользуемая переменная (Unused Variable) | Переменная объявлена/инициализирована, но не используется в действиях |
| **P4001** | WARNING| Недостижимый этап обработки (Dead Stage) | Этап никогда не выполнится из-за предшествующего `terminateOnMatch: true` или `DropEvent` |
| **P4002** | WARNING| Условие всегда истинно / всегда ложно (Constant Condition) | Условие тривиально сворачивается в константу на этапе компиляции |
| **P4003** | ERROR | Превышена максимальная глубина вложенности условий ($> 5$) | Упростите логическое дерево, вынесите подусловия в отдельные этапы |
| **P4004** | ERROR | Недопустимое число аргументов в `LogicalAnd` / `LogicalOr` ($< 2$ или $> 16$) | Логический оператор должен объединять от 2 до 16 условий |
| **P4005** | ERROR | Обнаружен цикл в графе выполнения (Non-DAG Control Flow) | Все переходы в конвейере должны быть строго направлены вперед |
| **E0000** | ERROR | Внутренняя ошибка компилятора (Internal Compiler Error) | Непредвиденное исключение при обработке узла |

### 4. Многопроходная архитектура валидации (Validation Pipeline)

Процесс компиляции состоит из 4 последовательных валидационных пассов и финальной фазы понижения (Lowering).
- **Принцип изоляции:** Ошибки **накапливаются** на каждом шаге (компилятор не падает на первой ошибке, а собирает полный спектр замечаний для UI).
- **Poisoning (Отравление типов):** При обнаружении фатальной ошибки в узле, узел помечается типом `Type.Poison`. Последующие пассы валидации игнорируют отравленные поддеревья, предотвращая лавинообразное порождение каскадных ложных ошибок.
- **Гейт перехода:** Фаза Lowering и построение `CompiledPipeline` запускаются **только при полном отсутствии ошибок (`severity == ERROR`)**.

```
                ┌────────────────────────────────────┐
                │        PipelineDefinition          │
                └─────────────────┬──────────────────┘
                                  │
                                  ▼
                ┌────────────────────────────────────┐
                │ Pass 1: Структурная валидация      │ ──▶ P1xxx ошибки/варнинги
                │ (Schema, IDs, Arity, Lengths)      │
                └─────────────────┬──────────────────┘
                                  │
                                  ▼
                ┌────────────────────────────────────┐
                │ Pass 2: RE2/J & ReDoS Guard        │ ──▶ P2xxx ошибки/варнинги
                │ (Pre-scan, RE2 Compile, Expansion) │
                └─────────────────┬──────────────────┘
                                  │
                                  ▼
                ┌────────────────────────────────────┐
                │ Pass 3: Типы, Контракты, Dataflow  │ ──▶ P3xxx ошибки/варнинги
                │ (Symbols, Definite Assign, Scopes) │
                └─────────────────┬──────────────────┘
                                  │
                                  ▼
                ┌────────────────────────────────────┐
                │ Pass 4: CFG, Reachability, Limits  │ ──▶ P4xxx ошибки/варнинги
                │ (DAG Check, Dead Stages, Budgets)  │
                └─────────────────┬──────────────────┘
                                  │
                           Есть ли ERROR?
                            /        \
                       ДА  /          \  НЕТ (Только WARNING/INFO или чисто)
                          ▼            ▼
               ┌────────────────┐   ┌────────────────────────────────┐
               │ Compilation-   │   │ Lowering Phase:                │
               │ Result.Failure │   │ 1. Аллокация слотов Frame      │
               └────────────────┘   │ 2. Специализация выражений     │
                                    │ 3. Разрешение переходов (PC)   │
                                    │ 4. Сборка CompiledPipeline     │
                                    └───────────────┬────────────────┘
                                                    │
                                                    ▼
                                    ┌────────────────────────────────┐
                                    │ CompilationResult.Success      │
                                    └────────────────────────────────┘
```

#### 4.1. Pass 1: Структурная валидация и проверка ограничений схемы (P1xxx)

Проверяет соответствие формальным ограничениям схемы DSL v1 без глубокого семантического анализа:
1. **Версия схемы:** `schemaVersion == 1`. Иные значения порождают `P1001`.
2. **Формат идентификаторов:**
   - `id` конвейера и всех стадий проверяются на маску `^[a-z0-9_-]{3,64}$`. При несоответствии — `P1002`.
   - Уникальность идентификаторов стадий: строится множество `seenStageIds`. При обнаружении коллизии формируется ошибка `P1003` с указанием дублирующегося `id` и `relatedLocations` на исходное объявление.
3. **Ограничения наполнения:**
   - `triggers.isNotEmpty()` (иначе `P1004`).
   - `stages.isNotEmpty()` (иначе `P1005`).
   - `stages.size <= 50` (аппаратный лимит Фазы 2, иначе `P1006`).
   - Для каждого этапа: `transforms.isNotEmpty() || actions.isNotEmpty()` (иначе `P1007`).
   - Длина строк: `name.length in 1..128`, `description.length <= 1024`.
4. **Ограничения логических условий:**
   - Проверяется глубина дерева условий $\le 5$ (иначе `P4003`).
   - Количество операндов в `LogicalAnd` / `LogicalOr` строго в диапазоне $2..16$ (иначе `P4004`).

#### 4.2. Pass 2: Валидация регулярных выражений, RE2/J и ReDoS Guard (P2xxx)

Обеспечивает математическую гарантию невозможности зависания горячего контура обработки уведомлений.

##### 4.2.1. Модель угроз ReDoS и гарантии RE2/J
Стандартный движок `java.util.regex` использует недетерминированный автомат с возвратом (Backtracking NFA), что делает его уязвимым к атакам экспоненциальной сложности $O(2^n)$ на таких шаблонах, как `(a+)+$`, `(a|aa)+$`, `(?:.*)+`.  
Компилятор `:pipeline:compiler` использует **RE2/J** — детерминированный конечный автомат (DFA/NFA без бэктрекинга), обеспечивающий:
- Строго линейное время матчинга **$O(n \cdot m)$**, где $n$ — длина входной строки, $m$ — число состояний автомата.
- Абсолютную устойчивость к катастрофическому откату.

##### 4.2.2. Алгоритм валидации Pass 2:
1. **Проверка лимита длины паттерна:**
   - Длина строки регулярного выражения $\le 256$ символов. При превышении — ошибка `P2001`.
2. **Предварительное сканирование на запрещенный синтаксис (Pre-scan):**
   До передачи в RE2/J паттерн анализируется легковесным токенизатором на наличие конструкций бэктрекинга:
   - Опережающие и ретроспективные проверки: `(?=`, `(?!`, `(?<=`, `(?<!` (ошибка `P2003`).
   - Обратные ссылки: `\1` .. `\9` (ошибка `P2004`).
   - Ревнивые и притяжательные квантификаторы: `++`, `*+`, `?+` (ошибка `P2003`).
   Точный диапазон запрещенного токена сохраняется в `TextSpan` для подсветки в редакторе.
3. **Синтаксический разбор через RE2/J:**
   - Вызывается `com.google.re2j.Pattern.compile(pattern, flags)`.
   - При выбросе `com.google.re2j.PatternSyntaxException` компилятор перехватывает его и преобразует в диагностику `P2002` с указанием точного смещения `errorIndex` в строке.
4. **Защита от раздувания размера автомата (Repetition Expansion Bomb):**
   - Анализируется AST скомпилированного регулярного выражения на предмет вложенных числовых повторителей (например, `(a{100}){100}`). Если произведение повторяющихся счетчиков превышает $1000$, выдается ошибка `P2005`.
5. **Оптимизация строковых литералов (Literal Lowering):**
   - Если строка паттерна не содержит специальных метасимволов (`.*+?^$()[]{}|\\`), компилятор формирует информационную диагностику `P2101` и на этапе Lowering заменяет регулярное выражение на сверхбыстрый `String.indexOf` / `String.startsWith`, полностью исключая оверхед регулярных выражений.

#### 4.3. Pass 3: Проверка типов, контрактов данных и Dataflow (P3xxx)

Отвечает за согласованность схемы данных, доступность переменных и типизацию.

##### 4.3.1. Модель данных и таблица символов (`SymbolTable`)
Выделяются два пространства имен:
- `input.*` — неизменяемые системные поля входящего уведомления (`input.packageName: String`, `input.title: String`, `input.text: String`, `input.postTime: Long`, `input.channelId: String?`). Доступны **только для чтения**. Запись в них порождает `P3003`.
- `ctx.*` — пользовательские контекстные переменные конвейера (`ctx.sanitizedText: String`, `ctx.parsedAmount: Long`, `ctx.resolvedCurrency: String`, `ctx.financialTransaction: FinancialTransaction`).

##### 4.3.2. Статический анализ Dataflow (Definite Assignment Analysis)
Поскольку конвейер Фазы 2 представляет собой направленный ациклический граф (DAG) с линейной последовательностью этапов и условным ветвлением, анализ определенности значений выполняется за **один топологический проход**:
- Состояние переменных в точке программы кодируется битовой маской `assignedMask: LongArray` (до 128 переменных).
- На входе конвейера маска содержит $0$ для всех переменных `ctx.*`.
- При прохождении этапа трансформации (`TransformDefinition`), записывающего `targetVar`, соответствующий бит устанавливается в $1$.
- В точках ветвления и слияния путей (после условных этапов, которые могут быть пропущены по `gate condition`):
  * **Strict Definite Assignment:** Переменная считается гарантированно инициализированной только если она инициализирована на **всех** возможных предшествующих путях исполнения (пересечение масок: $M_{\text{merge}} = M_1 \cap M_2$).
  * Попытка чтения переменной (`sourceVar`, `amountVar`, `currencyVar`), для которой бит в маске равен $0$, порождает фатальную ошибку `P3001` (Use Before Definition).
  * Если переменная определена на одном пути, но пропущена на другом ($M_1 \cup M_2 \neq M_1 \cap M_2$), компилятор формирует детализированную ошибку `P3002` с указанием этапа, на котором отсутствует инициализация.

##### 4.3.3. Анализ мертвого кода и неиспользуемых переменных (Liveness Analysis)
- Обратный проход (Backward May-Analysis): если переменная записана трансформацией, но ни в одном из последующих шагов или действий не прочитана, генерируется предупреждение `P3101 DeadStore`.
- Если объявленная переменная не используется в действиях, формируется предупреждение `P3102 UnusedVariable`.

##### 4.3.4. Проверка контрактов встроенных узлов (Node Contracts)
- **`AmountParse`:** Требует, чтобы `sourceVar` имел тип `String` (обычно результат `RegionalTextSanitize`). Записывает переменную типа `Long` (минимальные неделимые единицы валюты, Minor Units).
- **`CurrencyResolve`:** Требует строковый `sourceVar`. Записывает переменную типа `String` (3-символьный ISO код: "RUP", "MDL", "RUB", "EUR", "USD").
- **`FinanceExtract`:** Требует, чтобы входной пакет уведомления входил в список доверенных финансовых провайдеров (`allowedPackages`), либо предшествующий этап содержал предикат `PackageMatch`. Записывает структурированный объект транзакции.
- **`CreateTransaction`:** Проверяет обязательное наличие `amountVar` (тип `Long`) и `currencyVar` (тип `String`). При несоответствии типов генерируется `P3004`.
- **`SetCategory`:** Валидирует `confidence in 0.0..1.0` и корректность enum категории.

#### 4.4. Pass 4: Поток управления, достижимость и бюджеты сложности (P4xxx)

1. **Контроль ацикличности (DAG Invariant):**  
   Проверяется, что граф переходов содержит переходы **исключительно вперед**: $\text{targetStep} > \text{currentStep}$. Любая попытка циклического возврата блокируется ошибкой `P4005`.
2. **Анализ недостижимости (Dead Stage Detection):**  
   Если этап содержит безусловное действие `terminateOnMatch: true` (при отсутствии фильтра `condition == null` или при `condition == AlwaysTrue`), либо безусловное терминальное действие `DropEvent` / `StopProcessing`, все последующие этапы конвейера помечаются как недостижимые. Компилятор выдает предупреждение `P4001 DeadStageWarning` для каждого мертвого этапа.
3. **Свертка тривиальных условий (Constant Folding):**  
   Логические выражения `LogicalAnd(AlwaysFalse, ...)`, `LogicalOr(AlwaysTrue, ...)`, `LogicalNot(AlwaysTrue)` вычисляются на этапе компиляции. Ветви, которые никогда не выполнятся, отсекаются с выдачей предупреждения `P4002`.
4. **Верификация бюджета производительности компилятора:**  
   Компилятор измеряет общее время выполнения валидации и lowering.
   - **Бюджет времени компиляции на Poco M7 (HyperOS, энергоэффективные ядра Cortex-A55):** $\le 50$ мс.
   - **Бюджет на стандартной JVM десктопа:** $\le 5$ мс.
   - **Бюджет слотов памяти:** Количество объектных слотов `refSlots <= 128`, примитивных слотов `primSlots <= 64`. Превышение лимита вызывает `P4006 ComplexityLimitExceeded`.

### 5. Модель исполнения `CompiledPipeline` (Иммутабельный граф)

Скомпилированный конвейер оптимизирован под экстремальную производительность на горячем пути Android-устройства Poco M7.

#### 5.1. Регистровая модель памяти (`FrameLayout` и `Frame`)

Вместо медленного и вызывающего аллокации `Map<String, Any>` используется регистровая машина памяти:
- Все строковые и объектные переменные отображаются в плоский массив `refs: Array<Any?>`.
- Все целочисленные, логические и вещественные переменные отображаются в плоский массив примитивов `prims: LongArray` (без боксинга: `Boolean` хранится как `0L`/`1L`, `Double` упаковывается через `Double.doubleToRawLongBits`).
- Каждое скомпилированное регулярное выражение получает персональный слот в массиве `matchers: Array<com.google.re2j.Matcher>`. В горячем цикле вызывается только `matcher.reset(input)`, что гарантирует **0 аллокаций памяти** на каждый матч!

```kotlin
package com.example.npc.pipeline.compiler

import com.google.re2j.Matcher
import com.google.re2j.Pattern

/**
 * Описание раскладки регистровых слотов памяти конвейера.
 */
class FrameLayout(
    /** Количество слотов для ссылочных типов (String, CharSequence, DTO). */
    val refSlots: Int,
    /** Количество слотов для примитивных типов (Long, Boolean, Double bits). */
    val primSlots: Int,
    /** Количество предвыделенных матчеров RE2/J. */
    val matcherSlots: Int
)

/**
 * Переиспользуемый контекст исполнения для одного рабочего потока (Thread-Local / Pool).
 * Полностью исключает аллокации в цикле обработки уведомлений.
 */
class Frame(
    val layout: FrameLayout,
    patterns: Array<Pattern>
) {
    @JvmField val refs: Array<Any?> = arrayOfNulls(layout.refSlots)
    @JvmField val prims: LongArray = LongArray(layout.primSlots)
    @JvmField val matchers: Array<Matcher> = Array(layout.matcherSlots) { patterns[it].matcher("") }
    @JvmField val effects: EffectBuffer = EffectBuffer(capacity = 16)

    /**
     * Сброс состояния фрейма перед обработкой нового входящего события.
     */
    fun reset() {
        java.util.Arrays.fill(refs, null)
        java.util.Arrays.fill(prims, 0L)
        effects.clear()
    }
}
```

#### 5.2. Структура `CompiledPipeline`

```kotlin
package com.example.npc.pipeline.compiler

import com.example.npc.pipeline.compiler.stage.CompiledStage
import com.google.re2j.Pattern

/**
 * Иммутабельный скомпилированный конвейер.
 * Готов к потокобезопасному многократному исполнению в рантайме.
 */
class CompiledPipeline internal constructor(
    /** Уникальный идентификатор конвейера из DSL. */
    val pipelineId: String,

    /** Номер ревизии конвейера. */
    val revision: Long,

    /** Канонический SHA-256 хеш исходного AST для валидации целостности. */
    val canonicalHash: String,

    /** Временная метка успешной компиляции (System.currentTimeMillis()). */
    val compiledAtTimestamp: Long,

    /** Версия схемы исходного DSL (v1). */
    val dslVersion: Int,

    /** Версия компилятора. */
    val compilerVersion: Int,

    /** Быстрый пре-фильтр разрешенных пакетов (HashSet для O(1) проверки в Hot Path). */
    val packageWhitelistSet: Set<String>,

    /**
     * Битовая маска полей уведомления, реально требуемых конвейеру.
     * Позволяет NotificationListenerService извлекать из Android Bundle только нужные поля.
     * Бит 0: Title, Бит 1: Text, Бит 2: Sender, Бит 3: PostTime, Бит 4: ChannelId.
     */
    val requiredInputMask: Long,

    /** Раскладка памяти. */
    val layout: FrameLayout,

    /** Плоский массив скомпилированных этапов для прямого индексного вызова. */
    @JvmField internal val stages: Array<CompiledStage>,

    /** Массив прекомпилированных паттернов RE2/J. */
    @JvmField internal val patterns: Array<Pattern>,

    /**
     * Отладочная информация (Side-table).
     * НЕ используется на горячем пути исполнения, не занимает кеш-линии процессора.
     */
    val debugInfo: DebugInfo
) {
    /**
     * Точка входа горячего исполнения в рантайме.
     * Гарантирует выполнение в пределах заданного SLA без рефлексии и аллокаций.
     *
     * @param frame Предвыделенный контекст исполнения текущего потока.
     * @return Терминальный сигнал: [Signal.PASS] (успех), [Signal.DROP] (событие отброшено).
     */
    fun execute(frame: Frame): Int {
        val stageArray = stages
        var pc = 0
        while (pc >= 0) {
            pc = stageArray[pc].execute(frame)
        }
        return pc
    }
}
```

#### 5.3. Терминальные сигналы и контракт `CompiledStage`

```kotlin
package com.example.npc.pipeline.compiler

/**
 * Терминальные сигналы завершения работы конвейера.
 */
object Signal {
    /** Конвейер успешно завершен. Буферизованные эффекты должны быть закоммичены в БД. */
    const val PASS: Int = -1

    /** Событие подавлено/отброшено. Никакие побочные эффекты не применяются. */
    const val DROP: Int = -2

    /** Аварийная остановка (внутренняя ошибка этапа с изоляцией сбоя). */
    const val FAULT: Int = -3
}
```

Каждый этап представляет собой финальный класс, реализующий виртуальный метод `execute`:

```kotlin
package com.example.npc.pipeline.compiler.stage

import com.example.npc.pipeline.compiler.Frame
import com.example.npc.pipeline.compiler.Signal

/**
 * Базовый абстрактный класс этапа скомпилированного конвейера.
 */
abstract class CompiledStage {
    /**
     * Исполняет логику этапа.
     *
     * @param frame Контекст регистровой памяти.
     * @return Индекс следующего шага (PC >= 0) или терминальный сигнал (Signal.PASS, DROP, FAULT).
     */
    abstract fun execute(frame: Frame): Int
}
```

#### 5.4. Специализированные скомпилированные узлы (Zero Boxing Bytecode)

Вместо обобщенного интерпретатора с ветвлениями `when (node.type)` компилятор инстанциирует специализированные узлы прямого перехода:

```kotlin
package com.example.npc.pipeline.compiler.stage

import com.example.npc.pipeline.compiler.Frame
import com.example.npc.pipeline.compiler.Signal
import com.example.npc.pipeline.compiler.expr.BoolExpr
import com.example.npc.pipeline.compiler.expr.StrExpr
import com.google.re2j.Matcher

/**
 * Условный переход (Branch).
 */
class BranchStage(
    @JvmField val condition: BoolExpr,
    @JvmField val onTruePc: Int,
    @JvmField val onFalsePc: Int
) : CompiledStage() {
    override fun execute(frame: Frame): Int {
        return if (condition.eval(frame)) onTruePc else onFalsePc
    }
}

/**
 * Присваивание строковой переменной в регистровый слот.
 */
class AssignRefStage(
    @JvmField val targetSlot: Int,
    @JvmField val expr: StrExpr,
    @JvmField val nextPc: Int
) : CompiledStage() {
    override fun execute(frame: Frame): Int {
        frame.refs[targetSlot] = expr.eval(frame)
        return nextPc
    }
}

/**
 * Сопоставление с регулярным выражением через предвыделенный RE2/J Matcher.
 */
class RegexMatchExpr(
    @JvmField val matcherSlot: Int,
    @JvmField val inputSlot: Int
) : BoolExpr() {
    override fun eval(frame: Frame): Boolean {
        val input = frame.refs[inputSlot] as? CharSequence ?: return false
        val matcher = frame.matchers[matcherSlot]
        matcher.reset(input)
        return matcher.find()
    }
}

/**
 * Буферизация побочного эффекта (Action).
 */
class EmitEffectStage(
    @JvmField val effectType: Int,
    @JvmField val payloadSlot: Int,
    @JvmField val nextPc: Int
) : CompiledStage() {
    override fun execute(frame: Frame): Int {
        frame.effects.push(effectType, payloadSlot, frame)
        return nextPc
    }
}

/**
 * Терминирующий узел (Early Exit).
 */
class TerminateStage(
    @JvmField val signal: Int = Signal.PASS
) : CompiledStage() {
    override fun execute(frame: Frame): Int = signal
}
```

#### 5.5. Буфер эффектов (`EffectBuffer`) и двухфазный коммит

Действия над внешними системами (запись в Room, назначение категории, эмиссия событий в шину) буферизуются во `Frame.effects`:
1. При прохождении этапов действия складываются в компактный внутренний буфер `IntArray` без создания промежуточных DTO.
2. Если выполнение конвейера прерывается сигналом `Signal.DROP` или `Signal.FAULT`, буфер просто сбрасывается (`effects.clear()`). База данных и внешнее состояние приложения остаются абсолютно чистыми.
3. Если конвейер возвращает `Signal.PASS`, рантайм вызывает процедуру коммита:
   `StorageGateway.completeEventProcessing(eventId, frame.effects)`.

### 6. Спецификация JSONPath и подсветка ошибок в UI

Для точной подсветки проблемного поля в визуальном редакторе Compose компилятор строит канонический путь согласно спецификации **RFC 9535 (JSONPath Normalized Path)**.

#### 6.1. Правила построения нормализованного пути RFC 9535:
- Корневой элемент обозначается как `$`.
- Доступ к полям объекта оформляется строго в скобочной нотации с одинарными кавычками: `['fieldName']`.
- Доступ к элементам списков оформляется числовым индексом в скобках: `[0]`, `[1]`.
- Управляющие символы экранируются согласно RFC 9535 (`\'`, `\\`).

**Примеры нормализованных путей компилятора:**
```
$['stages'][0]['id']
$['stages'][2]['condition']['conditions'][1]['pattern']
$['stages'][2]['transforms'][0]['sourceVar']
$['stages'][1]['actions'][0]['confidence']
$['triggers'][0]['type']
```

#### 6.2. Координация с UI редактором (Compose Integration):
1. **Разрешение локации:**  
   UI компонент получает `CompilationDiagnostic`. Сначала он производит поиск визуальной карточки этапа по `diagnostic.location.stageId`. Это обеспечивает устойчивость UI: если пользователь добавляет или переставляет этапы местами, карточка этапа с ошибкой остается подсвеченной независимо от сдвига числовых индексов массивов.
2. **Точечная подсветка поля:**  
   Хвост пути после `stageId` (например, `condition.conditions[1].pattern`) определяет конкретный `TextField` внутри карточки этапа.
3. **Подсветка внутри строки (`span`):**  
   Для строковых полей (регулярные выражения, формулы) компилятор вычисляет полуинтервал `TextSpan(start, end)` в UTF-16 code units декодированной строки. UI передает его напрямую в `TextFieldValue(selection = TextRange(span.start, span.end))`, подсвечивая пользователю ошибочный символ красной волнистой линией.

### 7. Тест-план и Golden Suite верификации

Тестирование модуля `:pipeline:compiler` ориентировано на 100% детерминизм, математическую надежность защиты от ReDoS и полную эквивалентность эталонному конвейеру Фазы 1.1.

#### 7.1. Golden Suite: Эталонный пресет «Legacy 1.1»

Компилятор верифицируется на эталонном JSON-файле `preset-legacy-1.1.json`, определенном в спецификации DSL v1.
- **Тестовый сценарий:** Подача на вход `PipelineCompiler.compile(legacy1_1Definition)`.
- **Ожидаемый результат:**
  1. Результат строго является `CompilationResult.Success`.
  2. Список ошибок (`errors`) пуст.
  3. Список предупреждений (`warnings`) пуст.
  4. Сгенерированный `CompiledPipeline` содержит ровно 5 скомпилированных этапов:
     - `stage-fingerprint`
     - `stage-prototype-feedback`
     - `stage-bank-finance`
     - `stage-music`
     - `stage-communication`
  5. Скомпилированные RE2/J матчеры инициализированы и готовы к работе.
  6. Канонический хеш совпадает с зафиксированной эталонной константой ревизии.

#### 7.2. Набор тестов на защиту от ReDoS (Adversarial ReDoS Suite)

Тестовый набор содержит общеизвестные «злые» регулярные выражения (Evil Regexes), вызывающие экспоненциальный откат в стандартном `java.util.regex`:

```kotlin
val evilPatterns = listOf(
    "(a+)+$",
    "(a|aa)+$",
    "(a*)*",
    "^(a+)+$",
    "(x+x+)+y",
    "([a-zA-Z0-9_.-]+)+@([a-zA-Z0-9_.-]+)+",
    "(a|a?)+$",
    "(.*a){11}"
)
```

- **Тестовый инвариант 1 (Compile Phase):**  
  Все паттерны либо успешно компилируются через RE2/J за время $< 1$ мс на паттерн, либо корректно отвергаются пре-сканером с диагностиками `P2003` / `P2005`. Никаких `StackOverflowError` или зависаний компилятора.
- **Тестовый инвариант 2 (Execution Phase SLA):**  
  Для скомпилированных паттернов выполняется матчинг на враждебных входных строках вида `"aaaaaaaaaaaaaaaaaaaaaaaaaaaa!"` (длиной до 8192 символов).  
  **Требование:** Время исполнения одного матчинга на худшем входе строго $\le 50$ микросекунд. Нулевой катастрофический бэктрекинг!

#### 7.3. Fuzzing & Property-Based Testing (jqwik / Kotest Property)

- **Fuzzing мусорным AST:**  
  Генерация псевдослучайных мутированных структур `PipelineDefinition`:
  - Отрицательные таймауты, длины $> 100\,000$ символов.
  - Глубина логической вложенности от $1$ до $50$.
  - Зацикленные или пустые списки этапов.
  - Случайные UTF-8 и Unicode-суррогаты в паттернах.
- **Главный инвариант фаззинга:**  
  Метод `PipelineCompiler.compile()` **ни при каких входных данных не выбрасывает исключений в вызывающий код**. При любых повреждениях возвращается детерминированный `CompilationResult.Failure`.

#### 7.4. Архитектурный тест на чистоту зависимостей (ArchUnit / Bytecode Scanner)

Автоматизированный JVM-тест сканирует скомпилированный байткод JAR-артефакта `:pipeline:compiler`:
- Запрещено наличие любых вызовов или ссылок на пакеты:
  - `java.util.regex.*`
  - `kotlin.text.Regex`
  - `android.*`
  - `androidx.*`
- Нарушение теста приводит к немедленной остановке CI сборки.

### 9. План имплементации модуля `:pipeline:compiler` (Фаза 2.1)

1. **Шаг 1: Базовые контракты и структуры данных**
   - Реализация интерфейсов `PipelineCompiler`, `CompilationResult`, `CompilationDiagnostic`, `SourceLocation`, `TextSpan`.
   - Создание каркаса `FrameLayout`, `Frame`, `EffectBuffer` и абстракции `CompiledStage`.
2. **Шаг 2: Валидационные пассы**
   - Реализация `Pass1StructureValidator`: валидация схемы, форматов ID, лимитов вложенности.
   - Реализация `Pass2RegexValidator`: интеграция `com.google.re2j`, пре-сканер бэктрекинга, ReDoS-гварды.
   - Реализация `Pass3DataflowValidator`: таблица символов, анализ определенности присваивания (`Definite Assignment`), контракты узлов.
   - Реализация `Pass4ControlFlowValidator`: проверка ацикличности DAG, детектор мертвого кода, свертка тривиальных условий.
3. **Шаг 3: Генератор исполняемого графа (Lowering)**
   - Аллокатор регистровых слотов `FrameLayout`.
   - Специализация узлов (`BranchStage`, `AssignRefStage`, `RegexMatchExpr`, `EmitEffectStage`).
   - Построение итогового `CompiledPipeline`.
4. **Шаг 4: Тестирование и верификация**
   - Написание Golden-теста на пресете `preset-legacy-1.1.json`.
   - Реализация стресс-тестов ReDoS и фаззинг-тестов.
   - Проверка архитектурных ограничений через ArchUnit.

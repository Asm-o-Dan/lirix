## Required corrections

### F1 / P1 — legacy note content still satisfies the target through music_tracks

Both trees: `app/src/main/java/com/lirix/app/feature/lyrics/AutomaticLookupCoordinator.kt:32-35`. The note:user guard excludes cache fields, then unconditionally falls back to `track.plainLyrics`/`track.syncedLyrics`. This is an actual reachable legacy state: OfflineLyricsAdapter returns userNotes as plainLyrics (`LyricsProvider.kt:94-101` main), and the prior automatic path saved that result to both cache and music_tracks. Seed cache(provider=note:user, plainLyrics="private exact notes") and track(plainLyrics="private exact notes", userNotes="private exact notes"). `lookup(LYRICS, usable=true)` returns Available with zero provider calls. Chord-looking note text can similarly reach inline-chord detection. The real song never recovers.

The renderer repeats this fallback (`NowPlayingScreen.kt:1355-1356` main; canonical1365-1366). The merge repeats it (`LyricsDao.kt:61-65` main at reviewed snapshot; canonical49-53), treating the legacy duplicate as fresh real lyrics; changing only the target predicate therefore does not repair persistence. It can also leave note:user as provider for a newly recovered field when the duplicate is retained.

Minimum correction: consistently exclude track fields proven to be the same legacy note-origin payload when the current row identifies note fallback, including target detection, display and transactional merge/dual-write. Preserve independent real track lyrics and exact userNotes; do not clear unrelated cache/track data. Add a real Room fixture with nonblank legacy note payload in both tables, plus an independent real-track-field control. Assert actual provider acquisition, resulting real lyrics/provenance in both tables and unchanged notes; test the chord-looking note variant. The current note-only Room test stores null lyric fields and cannot detect this defect.

### F2 / P2 — observed offline completion is published as Incomplete

Both trees: `AutomaticLookupCoordinator.kt:151-158,165-180` (ForegroundLookupRecovery). Start an acquisition on usable network, send an unavailable snapshot during Loading, then finish the provider with an empty result while still offline. `coordinator.lookup` returns Incomplete from its captured usable=true request; line174 publishes it without checking the current network. The UI reports “Search could not be completed” although unusable Internet was actually observed. An already incomplete target likewise stays Incomplete when the monitor reports an outage.

Minimum correction: publish WaitingForNetwork for a still-missing terminal result when the current snapshot is unusable, retain the outage arm and existing pending recovery semantics, and do not replace an actually satisfied Available state. Add a controlled state-machine test that completes while offline, verifies Waiting, restores validated connectivity, and verifies exactly one recovery. The current pending-reconnect test restores connectivity before completing the first request, so it misses this case.

### F3 / P2 — the foreground remains Loading while a cancelled provider unwinds

Both trees: `AutomaticLookupCoordinator.kt:67-82,86,94-101,112-117`. The logical deadline wraps the shared job, but every subscriber directly awaits its completion. A blocking/noncancellable provider cannot complete that Deferred until its unwind finishes; the foreground therefore continues Loading beyond its logical deadline. This contradicts §5's separate requirement that UI stop observing promptly, while respecting the spec's explicit allowance for physical network unwind.

The existing `lateNonCancellableAcquisitionAfterDeadlineCannotCommitAndGateIsReusable` test models deadline100/delay200, but asserts only the result after completion; it does not assert phase/elapsed time at100. Its prevention of a late commit is useful and should remain.

Minimum correction: bound the subscriber's observation independently from the shared job's physical completion, yield a terminal unresolved phase promptly, preserve shared ownership/coverage and do not launch a duplicate chain while the old job still executes. Add a scheduler assertion that foreground exits Loading at the logical budget while acquisition is still unwinding, cannot commit after cancellation, and later explicit work respects the registry. No socket cancellation framework or hard physical runtime guarantee is requested.

### F4 / P2 — blank stored chords hide recognized inline chords

Both renderers: `NowPlayingScreen.kt:1432-1433` main. The chord branch uses `validCache?.chordsAmDm ?: detectInline(effectivePlain)`, whereas the target predicate correctly treats blank/whitespace stored chords as missing and recognizes inline chords in real lyrics. Seed an existing partial row with chordsAmDm="" and real lyric text containing recognized inline chords. The coordinator reports Available/no HTTP, but the renderer bypasses inline detection because the blank string is non-null, shows the missing-target branch and offers Retry for a satisfied target.

Minimum correction: filter blank stored chords before the inline fallback and add a production renderer assertion for this partial-row case. This is a small consistency correction within the existing chord branch; no parser changes are needed.

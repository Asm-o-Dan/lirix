# Antithesis: профиль, аватар и расширенная аналитика — 2026-10-27

Read-only source audit; no code, build, device, remote services or user data accessed. Baseline HEAD `1a3fc86`; working-tree deltas are explicitly identified below. Conclusions are about available records and static algorithms, not measured user behaviour.

## What the data cannot establish

1. **Genre is not recorded.** `shared/src/commonMain/kotlin/com/lirix/app/storage/MusicEntities.kt:26-41` TrackEntity contains track key, title, artist, album, source package, aggregates, notes, favorite, lyrics and artwork; there is no genre, tag provenance or confidence. `:56-68` ListeningSessionEntity has no genre either. Genres cannot be inferred accurately from artist or song title; artists can span several genres, and online catalogs may disagree. Do not present a genre until there is explicit user-supplied or opt-in sourced per-track metadata with provenance, unavailable/unknown state, and clear tie/multiple-genres rule. This does not establish whether third-party metadata APIs are available or licensed.
2. **A skip and dislike are not identifiable from stored listening sessions.** The same entity `:56-68` has source, start/end/duration/completed/optional interval JSON, but no event reason, explicit next command, original media length or user intent. `app/src/main/java/com/lirix/app/ingestion/MediaSessionCollector.kt:735-745` sends a next command but is not proof that external player transitions outside Lirix represent user skips. Pause, source interruption, external player autoplay, seeking or manual next could all appear as short sessions. Do not calculate historical skip rate as truth or name a song “most disliked”. If later instrumented, offer “often skipped” with definition, unknown-end exclusions and source/coverage disclosure; no sentiment inference. Require an informative minimum exposure and per-track count, e.g. at least 5 eligible starts and 3 observed deliberate skips, make thresholds product-configurable, not statistical proof.
3. **Playback counts are session/track aggregates, not validated full listens.** HEAD `shared/src/commonMain/kotlin/com/lirix/app/analytics/WrappedStatsEngine.kt:221-245,253-268` groups sessions by track, labels their number as plays and ranks artists by count then duration; it does not prove a full-track listen or a favorite. `:305-325` all-time fallback uses aggregated `playCount` and `totalDurationMs`; those are a different basis when no sessions exist. `TrackEntity` `MusicEntities.kt:33-38` contains both a counter and `isFavorite`; automatic favoriting can also happen in worktree `app/src/main/java/com/lirix/app/feature/MonotonicSessionRecorder.kt:78-88` (untracked), so a heart is not necessarily an explicit user preference. Label rankings “most played in recorded history” and specify period/count basis; do not claim completed listens or a user's actual favorite based on a ranking alone.
4. **Historical coverage and timing are uncertain.** `MusicEntities.kt:65-68` defines empty interval JSON as legacy history with unknown pauses. Current **untracked** `shared/src/commonMain/kotlin/com/lirix/app/analytics/ListeningIntervals.kt:21-30` bounds legacy data by its recorded span but cannot reconstruct pauses, and `:33-37` drops ambiguous wall-clock correction gaps. Current **dirty** `WrappedStatsEngine.kt:419-420` indicates legacy history. Neither is proof of the committed HEAD implementation or installed 1.5.1 behavior. In HEAD `WrappedStatsEngine.kt:168-181` period filtering uses session start; a session crossing midnight/period boundary may be excluded or fully attributed to the wrong period. Worktree revised projection `WrappedStatsEngine.kt:147-153` and `ListeningIntervals.kt:52-74` change this behaviour but have not been established as part of HEAD here. Gate any new time analytics on the actual deployed recorder, known-coverage detection, tests for pause/seek/process death/midnight, and disclose incomplete legacy history.
5. **Periods and artist identity affect rankings.** In HEAD `WrappedStatsEngine.kt:168-180`, “week”/“month” mean rolling 7/30 × 24 hours, while Today is local day. Current untracked `ListeningIntervals.kt:78-86` computes daily boundaries using the current system time zone; changes of zone can alter historical day attribution. Both current and HEAD artist rankings trim strings but group by exact text (`WrappedStatsEngine.kt` worktree `:212-219`, HEAD `:253-260`), so spelling/casing, collaborations, romanization and metadata corrections can split or conflate artist results. `shared/src/commonMain/kotlin/com/lirix/app/feature/music/MusicTrackParser.kt:316-319` in dirty worktree hashes lowercase trimmed title|artist|album; different album names or editions may split the same song; identical metadata can merge distinct recordings. Recheck HEAD line numbers before applying this finding: MusicTrackParser is dirty. An explicit identity/matching policy and visible period/measurement basis are required before confident cross-source leaderboards.
6. **Cross-device and archive data are not an unquestioned ground truth.** HEAD `shared/src/commonMain/kotlin/com/lirix/app/storage/LibraryArchive.kt:51,55-61` identifies a session by `(trackKey, sourcePackage, startTimeMs)` and merges collisions; `:69-78` uses maxima for track aggregates and session counts. These are reasonable conservative rules but do not prove identical listening events across devices or deduplicate different timestamps from overlapping sessions. Worktree archive `:62-69` introduces interval-aware merging and is separately dirty. Do not promise cross-device rankings until the merge version and provenance/overlap handling are tested.

## Avatar, privacy, and UX recommendations

- Keep an explicit neutral default and user-selected preset, with optional auto mode. Freeze a displayed avatar until the user requests refresh or define an explicit stable period, deterministic tie-break by stable identifiers, and persist the chosen preset so trivial rank changes or localization do not silently change identity. Use abstract non-identifying imagery: do not derive a recognizable performer portrait or user photo from artist metadata, and do not claim association with an artist.
- Start with already measured, explainable values: tracked minutes and unique tracked songs for a selected period, a measured top performer labelled “most played”, and already persisted unlocked achievements (`MusicEntities.kt:103-116`), only after checking what code/version produced each value. Small sample: show actual totals but suppress comparative labels/rankings until a disclosed threshold, e.g. ≥10 qualifying sessions across ≥3 different tracks; this is a UX proposal, not statistical validation. No user identity, account, new personal demographics, provider enrichment, analytics export, or sync is necessary to try the local profile.
- Provide “not enough data” and legacy/incomplete history states instead of invented genre, zero-as-fact, or labels about personality/dislike. Explain that source apps and observation periods affect coverage; users can manually select appearance, opt out, and see what data drive a badge. Store local by default. Future export/sharing should have explicit preview and consent, and backup/restore should preserve explicit choices without leaking private track names by default.
- Verification before shipping: controlled fixtures for one versus five sessions, metadata collisions/collaborations, missing IDs, period boundaries/midnight/timezone/DST, pause/seek/restart and legacy rows, duplicate/overlapping cross-device sessions, zero/missing genre and insufficient evidence. Assert no skip/dislike shown without explicit eligible observations; avatar remains stable and manual choice survives restart/backup. Test RU/EN and large type. Tests currently not run.

# Ревью тяжёлых проблем: безопасность, данные, производительность — 2026-11-13

Запрос владельца: найти в плане и коде самые тяжёлые инженерные проблемы и решить их. Ревью выполнено по рабочей копии `codex/release-1.5.1` (со всеми незакоммиченными потоками). Ничего не закоммичено.

## Исправлено

### 1. Импорт набора правил включал чужое правило и мог перезаписать своё (безопасность, приватность, AGENTS 7.1)
Было: `ScraperRuleBundleCodec.deserializeAndValidate` создавал правило без статуса (движок читал это как ACTIVE) с `isEnabled = true` и брал `id` из файла; `saveRule` работает как REPLACE. Вставленный JSON сразу начинал фоновые запросы к своему сайту для каждой песни (раскрывая, что слушает пользователь) и мог молча заменить существующее правило с тем же `id`. «Контрольная сумма» — обычный хеш без ключа, подлинность не подтверждает.

Стало:
- Android: импорт всегда даёт DRAFT под новым `id`; автоматический каскад черновики не исполняет. В диалоге импорта правило проверяется на текущей песне Teach Mode тем же движком, что и собственные правила, и включается только при успехе без WebView (`TeachRuleFactory.canActivate`); иначе остаётся черновиком с объяснением. Ошибка сохранения показывается, а не теряется.
- Desktop: импорт под новым `id` и выключенным (`isEnabled = false`); включение — флажком в списке источников.
- Файлы: `feature/lyrics/ScraperRuleBundleCodec.kt`, `ui/components/ScraperRuleDialogs.kt`, `ui/TeachModeScreen.kt`, `desktop/.../DesktopRuleBundles.kt`.
- Тесты: `ScraperRuleBundleCodecTest` — черновик не делает ни одного запроса; после `activated` выполняется поиск по домену правила; `id` из файла не используется повторно.

### 2. «Отменить» после очистки чёрного списка безвозвратно теряла историю прослушиваний (потеря данных)
Было: `BlacklistPurgeEngine` удалял сессии и треки, а для отмены сохранял только треки. Отмена возвращала треки без истории: время и счётчики в «Итогах» пропадали навсегда. Очистка шла порциями без транзакции (при сбое — треки без истории или история без треков), хотя в комментарии называлась атомарной.

Стало: очистка и отмена выполняются в одной `libraryTransaction`; копия включает сессии (`PurgeBackup`); отмена возвращает сессии с исходными идентификаторами, не трогает сессии, записанные после очистки, и не перезаписывает трек, который успел появиться заново. Повторная отмена ничего не дублирует.
- Файлы: `feature/blacklist/BlacklistPurgeEngine.kt`, `ui/blacklist/BlacklistViewModel.kt`, `shared/.../storage/MusicDao.kt` (два запроса, схема не менялась).
- Тесты: `BlacklistPurgeEngineTest` — три новых случая.

## Проверено, изменений не требуется
- Подмена DNS после проверки адреса в `RuleNetwork` (проверка адресов и соединение разрешают имя отдельно): запросы только по HTTPS с проверкой сертификата, внутренний узел не предъявит действительный сертификат для чужого домена. Практической атаки нет.
- Обновления через GitHub: фиксированный префикс URL, сверка SHA-256 и подписи APK с установленной, проверка варианта сборки.
- Манифест: экспортированы только `MainActivity` и служба уведомлений под системным разрешением; cleartext не разрешён; `allowFileAccess = false` в обоих WebView; собственных `TrustManager` нет.

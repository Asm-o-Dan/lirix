## Н1. «Не тот текст» / «Не те аккорды» — перейти к следующему источнику (У2)

Сейчас: в движке есть `MusicFeatureEngine.rejectCurrentLyrics` / `undoLyricsRejection`, таблица `lyrics_rejections` и тест `LyricsRejectionCascadeTest`, но в интерфейсе действия нет (и в истории Git его не было). Отдельного отклонения аккордов нет.

Что сделать:
- Действие в меню текста плеера: «Не тот текст — искать дальше»; для аккордов — «Не те аккорды — искать дальше». Показывать только когда текущее содержимое получено автоматически. Ручной текст, правка (`USER:EDIT`), привязка из Teach Mode и разметка студии не отклоняются и не стираются (AGENTS 7.1).
- Исправить движок: сейчас `rejectCurrentLyrics` безусловно стирает текст трека и кеш. Нужно: не трогать ручное содержимое; отклонять текст и аккорды раздельно (источник аккордов не обязан совпадать с источником текста); старое содержимое убирать только после того, как решение об отклонении записано.
- Согласовать с `AutomaticLookupCoordinator` (общий шлюз поиска, фоновые повторы): отклонённый источник не возвращается при восстановлении сети и при предзагрузке.
- После перехода — сообщение с названием нового источника и «Отменить» (возврат прежнего текста). Если источники кончились — честное «Больше источников нет» и предложение Teach Mode.
- Desktop: проверить паритет (общая таблица, архив библиотеки уже переносит отклонения).

Приёмка: неверный текст → следующий источник; повторное нажатие идёт дальше по каскаду; отмена возвращает прежний; ручной текст и тайминги студии не затронуты; отклонение переживает перезапуск, восстановление сети и архив; аккорды отклоняются независимо от текста.

## Н2. Автогенератор правила в Teach Mode: «зайти на сайт и нажать одну кнопку» (У2)

Цель: пользователь открывает страницу песни и нажимает «Создать правило для сайта». Выделять блок вручную не нужно.

Что уже есть: шаблон поиска из навигации пользователя (`SearchTemplateDetector`), ранжирование выдачи (`RuleCandidateRanker`), проверка правила полным потоком и запрет включения без проверки (`CustomRuleLyricsProvider.resolve`, `TeachRuleFactory.canActivate`), golden-фикстуры четырёх сайтов.

Что добавить:
1. Автоопределение блока текста на странице (чистая функция на Jsoup, без сети): оценка кандидатов по плотности строк, доле ссылок, переносам, совпадению с названием песни в заголовке; для аккордов — доля строк с аккордами (`pre`, моноширинные блоки). Результат — селектор, устойчивый к соседним страницам (класс/атрибут, а не позиция), и список вычищаемых блоков (реклама, кнопки).
2. Обобщение селектора: проверка на второй песне того же сайта. Генератор сам находит вторую песню через шаблон поиска (другой трек из медиатеки) и убеждается, что селектор даёт текст и там. Не прошло — правило остаётся черновиком с объяснением.
3. Шаблон поиска без участия пользователя: если пользователь пришёл из поисковика и по сайту не искал — попробовать форму поиска страницы (`form` с `input[type=search]`, `role=search`, OpenSearch-описание). Не нашлось — попросить один раз выполнить поиск на сайте.
4. Экран: одна кнопка → ход проверки по шагам (блок найден → поиск найден → проверено на 2 песнях) → «Включить». Ручной режим выбора остаётся как запасной путь.
5. Отказы: защищённые и динамические сайты (403/429, содержимое только после скриптов) → черновик и ручная привязка текста к песне; CAPTCHA не обходится.

Независимый оракул для тестов: фикстуры страниц с вручную записанным ожидаемым текстом (как в `fixtures/rules/`), плюс «плохие» страницы: список песен вместо песни, страница с комментариями длиннее текста, две колонки (оригинал и перевод).

Приёмка: на четырёх сайтах из фикстур правило создаётся без ручного выделения и проходит проверку на двух песнях; на «плохих» страницах генератор отказывается, а не создаёт мусорное правило; неуверенное совпадение не активируется (AGENTS 7.4).

## Н3. Хаб сообщества: LRC из студии и переводы, лайки, жалобы (У2, новая серверная часть)

Цель: пользователи выкладывают тайминги из студии и переводы; клиент сначала берёт одобренное сообществом, чтобы не нагружать ни человека, ни модель перевода.

Требования владельца: лайки; при выборе версии приоритет у залайканных; при жалобах — блокировать автору возможность отправлять.

Это первое серверное звено проекта, сейчас Lirix полностью локальный. Нужны отдельная спека и решения:

- **Что публикуется.** Тайминги (метки времени, привязанные к отпечатку текста) почти не содержат чужого контента; текст песни и перевод — чужие произведения. Рекомендация первого шага: публиковать только тайминги и переводы, сделанные самим пользователем, а текст оригинала не раздавать (клиент накладывает тайминги на текст, полученный из своих источников, по отпечатку).
- **Идентичность.** Без аккаунтов — анонимный ключ устройства (Ed25519 уже есть в Connect) с ограничением частоты; лайки и жалобы привязаны к ключу. Блокировка отправки — по ключу; это обходится переустановкой, поэтому вес лайка нового ключа мал, а новые отправки сначала видны не всем.
- **Ранжирование.** Не «сумма лайков», а нижняя граница доверительного интервала (Wilson), чтобы одна оценка не побеждала сотню; ручной выбор пользователя всегда важнее рейтинга (AGENTS 7.1); версия сообщества не заменяет ручной текст.
- **Жалобы.** Порог скрытия версии и порог блокировки автора; защита от злоупотребления (жалобы от свежих ключей весят меньше); журнал решений и возможность оспорить.
- **Приватность.** Запрос к хабу раскрывает, что слушает пользователь: только по явному включению; запрос по отпечатку трека, без истории и идентификаторов устройства сверх ключа.
- **Сервер.** Размещение, стоимость, резервные копии, модерация и ответственность за контент — решение владельца.

Этапы: спека и модель угроз → сервер (минимум: отправка, выдача по отпечатку, лайк, жалоба) → клиент Android (отправка из студии и из панели перевода, выдача в каскаде перед машинным переводом) → Desktop.
